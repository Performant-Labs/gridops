# Handoff-A: Phase 3 - GitLab Docker pool default image and no runner group (#172)  (up-front plan review)

**Date:** 2026-11-21
**Branch:** claude/gitlab-172-pool-image-bb7d36
**Brief reviewed:** docs/handoffs/172-brief.md   **Reuse map:** none (no survey.md for #172; the brief's Scope section and handoff-D's "Evidence" line stand in for it)   **Wireframe:** docs/handoffs/172/wireframe.html
**Verdict:** BLOCK

## Summary
Most of the plan extends the right objects. On the server it threads a `gitlab` fact into `validate_pool_configuration`, the way `macos_runtime` already relaxes the Tart image rule. On the frontend it puts the platform difference on the descriptor and resolves it through `platformForPool` or the selection. Two plan elements block. (1) The brief's runner-group mechanism cannot produce its own Done-when. `buildCreatePayload` merges GitHub's partial, which always sends `runnerGroupId: 1`, and the shared zod `runnerGroupId ... .default(1)` adds it back. So removing the key from GitLab's `toCreatePayload` changes nothing on the wire. (2) The plan leaves a second, platform-unaware default-image path in place: the Fleet execution editor's `defaultImages`. With an empty GitLab pool image, that path pre-fills the **GitHub** runner image into the pool's fleet Docker platform. This is the defect class the issue exists to remove, and it bypasses the server's single resolver, `docker_runner_image`.
