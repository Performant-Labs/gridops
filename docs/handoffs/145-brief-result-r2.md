### WARN findings

**[W-1]** The acceptance criterion for payload equality says Vitest `toEqual` on the `data` object with "keys set to `undefined` count as absent (as `JSON.stringify` drops it)." This relies on `toEqual` treating `{ repositoryIds: undefined }` as equal to `{}`. In Vitest, `toEqual` recursively checks equality and does treat `undefined` properties as equal to absent properties (matching Jest's `toEqual` behavior). However, this is a subtle behavior that could be mistaken for `toStrictEqual` (which distinguishes `undefined` from absent). Recommend adding an explicit note in the test file or criterion clarifying that `toEqual` is intentional and `toStrictEqual` must not be substituted.

**[W-2]** The brief requires "no in-app link or redirect targets a redirecting route" and lists specific links, but the acceptance criterion only checks `runner-pools.new.tsx` line 368, `webhooks.tsx` line 83, `settings.index.tsx` line 10, and `settings.tsx` lines 41-42. Other links to the GitHub settings page may exist elsewhere in the codebase (e.g., in error messages, empty states, or documentation). The grep criterion ("no remaining `"/settings/github"` or `"/settings/integrations"` string outside the two redirect-only route files") covers string literals but may miss dynamically constructed links or links using route constants. Recommend adding a check for dynamically constructed links or route references (e.g., `to="/settings/github"` in a variable).

**[W-3]** The brief requires the Connections page to support a post-create one-time reveal dialog "generically" but notes "GitHub/Bitbucket may not use it today." The acceptance criterion tests it with a "test-only descriptor." However, the test-only descriptor must be injectable into the page ("The page component takes the descriptor list as a prop (default: the production `platforms`) so tests can inject a test-only descriptor with a post-create hook without adding it to production"). This is a design decision that the brief documents, but the acceptance criterion does not specify whether the test is a Vitest unit test or a Playwright walkthrough. If it is a Vitest test, the page component must be renderable in isolation with mocked route context. Recommend clarifying whether the post-create reveal dialog test is a Vitest component test or a Playwright walkthrough, and if Vitest, what route mocking is required.
