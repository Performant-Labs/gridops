### WARN findings

**[W-1]** The brief's acceptance grep exclusion for the two redirect-only route files matches the whole line `^export const Route = createFileRoute\("/settings/(github|integrations)"\)\(\{$`. If the implementer adds a comment to the same line (e.g. `export const Route = createFileRoute("/settings/github")({ // redirect`) — which is a natural response to the instruction "the rest of the route object follows on later lines" — the grep prints a hit and fails the criterion. The brief's own example of a later-line change ("the line changes only if someone edits it by hand") acknowledges the line can change, but the criterion treats any change as failure. Consider specifying that the exclusion regex should be anchored to the route declaration string rather than the whole line, or that a comment on the declaration line is explicitly prohibited.

**[W-2]** The brief states "The test file must typecheck against that `types.ts` declaration (`npm run typecheck`)" for the post-create reveal criterion, but the `npm run typecheck` script is `tsc --noEmit`. TypeScript's `--noEmit` does not run Vitest's `expectTypeOf` assertions (those are runtime type-level checks executed by Vitest). The criterion says `npm run typecheck` checks the `expectTypeOf` assertion, which is incorrect: `expectTypeOf` is a Vitest feature, not a TypeScript compiler feature. The assertion is checked when Vitest runs the test, not when `tsc` typechecks. The brief must either (a) change the criterion to say the test passes under `npm test` (Vitest), or (b) acknowledge that `expectTypeOf` is a runtime type assertion and is not exercised by `tsc`.

**[W-3]** The brief's acceptance grep for the partial-load criterion uses `grep -niE "github|bitbucket" src/features/runner-pools/targets-row.tsx src/features/runner-pools/platform-options-section.tsx src/features/platform-connections/connections-section.tsx`. This will also match legitimate non-platform-specific content such as "GitHub" in a test fixture name, "Bitbucket" in a comment, or "github" in a variable name. The criterion says "comments included," but the pass condition is that the grep prints nothing, which means no comment in those files may mention GitHub or Bitbucket even to explain why the code is platform-neutral. This may be overly restrictive; consider allowing comments or excluding comment-only matches.

**[W-4]** The brief states in the "Connections page loading" section that `getBitbucketConnections()` "does not accept the `queryFn`'s `signal` as written," yet the criterion for partial-load failure says the test asserts "clicking Retry makes exactly one more request to that endpoint and no other request" using a stubbed `fetch`. The criterion does not require the Bitbucket descriptor's list binding to accept or use the `AbortSignal`; it only requires that the binding be an async function of the signal that can reject. If the binding wraps `getBitbucketConnections()` and passes the signal to a function that ignores it, the test may still pass. Consider adding a criterion that the Bitbucket descriptor's fetching binding is an async function that accepts and forwards the `AbortSignal` (or explicitly state that the binding may ignore the signal for now).
