## Brief Review (Round 1)

### BLOCK findings

**[B-1]** The brief requires "GitHub App setup (admin-only) may stay as a section on this page" (Required design 2) but then the Architecture decisions require "The sections of `src/routes/settings.github.tsx` move verbatim to `src/features/platform-connections/github-app-section.tsx`, receiving settings data from the route through props" (Reuse map). These are not contradictory, but neither specifies what happens to the `/settings/github` route's loader and action logic (e.g. `syncGitHubAction()`, `createGitHubAppManifestAction()`). The acceptance criterion "Every existing flow still works: … managing the GitHub App" cannot be verified without specifying how the GitHub App section's actions are invoked from the new Connections route. — Must specify how the GitHub App section receives and invokes its actions (props? route-level action functions?) and where the loader data comes from when `/settings/github` becomes redirect-only.

**[B-2]** The brief states `pool-plan-preview.tsx` "takes the target sentence as a prop (computed from target kinds) instead of branching on `scope`; it never imports the registry" (Reuse map). But the SOURCE EXCERPTS do not include `pool-plan-preview.tsx`. The brief's "Verified platform-branching sites" lists `src/components/pool-plan-preview.tsx` line 50 as a site that must be changed, and the acceptance criterion "The new-pool form and pool settings have no platform-specific rows outside Targets and Platform options" implies this change. However, the claim that `pool-plan-preview.tsx` "never imports the registry" while still getting "the target sentence" is consistent, but the brief does not show what `pool-plan-preview.tsx` currently does at line 50 or whether "target sentence as a prop" is sufficient to preserve existing behavior. Without the excerpt, the acceptance criterion "Every existing flow still works: GitHub repository pools; GitHub runner-group pools" cannot be traced to a testable plan for `pool-plan-preview.tsx`. — Must show the current `pool-plan-preview.tsx` line 50 content and specify how the target-sentence prop is computed and passed.

**[B-3]** The brief mandates "The submitted payload must be what the old form would have sent for the same selection, defined as: the `data` object passed to `createRunnerPoolAction` (new-pool form) or `updateRunnerPoolAction` (pool settings) is deep-equal (Vitest `toEqual`) to the object the old form built for the same selection." The "old form" no longer exists after this change (the rows are removed/replaced), and the brief does not specify a frozen reference implementation, snapshot, or fixture that captures the old form's output. The acceptance criterion "Vitest payload-equality cases … for: GitHub repository pool, GitHub organization runner-group pool, GitHub repositories plus Bitbucket workspaces, and pool-settings saves for a repository pool and an organization pool" cannot be tested because the comparator (the old form's output) is not preserved anywhere. — Must specify where the old form's expected `data` objects are captured (e.g. as fixtures in `tests/fixtures/` or inline constants in the test) and ensure they are derived from the pre-change behavior, not from the new implementation.

**[B-4]** The brief's Target-kind contract states: "update omits `installationId`, `scope` and `bitbucketConnectionIds`, sends `repositoryIds`/`priorityRepositoryIds`/`priorityWaitMinutes` only for repository pools (else `undefined`), and `runnerGroupId: runnerGroupId || pool.runnerGroupId` for organization pools, else `1`." The SOURCE EXCERPTS for `schemas.ts` show only lines 156–194, which do not include `createRunnerPoolSchema` or `updateRunnerPoolSchema` definitions (the `scope`, `installationId`, `repositoryIds`, `runnerGroupId`, `priorityRepositoryIds`, `priorityWaitMinutes` fields are referenced but not shown). The brief's own "Verified facts" section says "the settings form's `repositoryIds: undefined` for organization pools" but does not show the update schema or the old settings form's submit logic. The claim that update "omits `installationId`, `scope`" and sends `runnerGroupId: 1` for repository pools (the "else `1`") is a specific behavioral claim about the old form that the shown excerpts do not support. If this is wrong, the new form will send different payloads and break existing flows. — Must show the `updateRunnerPoolSchema` definition (or the old settings form's submit code, `runner-pools.$poolId.settings.tsx` lines 122–144 per the brief's own reference) to confirm the exact field set and defaults for each pool type, and freeze those as expected fixtures.

### WARN findings

**[W-1]** The brief says "Each redirect points directly at `/settings/connections` — no redirect chains" and lists `/settings/integrations`, `/settings/github`, and `/platform-connections`. But it also says to repoint "the `Settings → Integrations` link in `runner-pools.new.tsx` (line 368)" directly at Connections. The acceptance criteria only test the three redirects, not that `runner-pools.new.tsx` line 368 and `webhooks.tsx` line 83 point directly at `/settings/connections` without a hop. Recommend adding an acceptance criterion that `runner-pools.new.tsx` and `webhooks.tsx` link directly to `/settings/connections` (not through a redirecting route).

**[W-2]** The brief's "Connections page loading" requires `Promise.allSettled` per platform with per-platform Retry. This is a runtime behavior claim that depends on the route loader implementation. The acceptance criteria do not include a test for partial load failure (one platform failing while another succeeds). Recommend adding an acceptance criterion: a Vitest (or Playwright) test where one platform's loader rejects and the page still renders the other platform's connections with a Retry control.

**[W-3]** The brief says "Bitbucket workspace is **not standalone** — it requires a GitHub target, because `createRunnerPoolSchema` requires `installationId > 0` and a `scope`." This is described as a correction to wireframe D5, but no acceptance criterion verifies that the picker disables Bitbucket options until a GitHub target is chosen. The "targets picker's mixing rules" test (acceptance criterion 5) may cover this, but it is underspecified. Recommend making the mixing-rules test explicitly include "Bitbucket workspace disabled with reason until a GitHub target is selected."

### NIT findings

**[NIT-1]** The brief says "the wireframe's C4 note '(or Esc)' is wrong: only the button closes it" (Reuse map, SecretDialog). This is a binding correction, but the brief does not say whether the wireframe document itself should be updated to remove "(or Esc)". Recommend stating whether the wireframe is a living artifact to be corrected or a historical reference.

**[NIT-2]** The brief's "Operating rules" says "Implement against the failing tests from Phase 5 — F writes no tests." This implies a Phase 5 artifact (test files) exists or will be provided before implementation. The brief does not specify where those tests live or whether they are in the same worktree. Recommend clarifying the handoff path for Phase 5 test artifacts.

### Verdict
