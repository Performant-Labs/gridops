### BLOCK findings

**[B-1]** The acceptance criterion for `?appError=` handling requires a test assertion that "without `appError` it still redirects to `/settings/general`", but the brief does not show the code path for this case. The shown excerpt (`settings.index.tsx` lines 4-13) only includes the `appError` branch (lines 8-11); the fallback redirect is stated as a claim ("without `appError` it still redirects to `/settings/general`") but the excerpt is bounded and does not show lines 12+. This is a testable criterion, but the test's expected value is asserted from prose, not from a shown source. A test written against a wrong fallback target would pass its own assertion but fail in production. The brief must either include the full `settings.index.tsx` excerpt showing the fallback redirect target, or the acceptance criterion must reference the exact line number that will be shown in the diff gate.

**[B-2]** The acceptance criterion requiring "no remaining `"/settings/github"` or `"/settings/integrations"` string outside the two redirect-only route files" creates an unenforceable pass/fail boundary. The brief states the grep is run "excluding `routeTree.gen.ts` and `/api/v1/` paths" (under "References to the redirecting routes"), but the acceptance criterion text says "the gitignored generated `src/routeTree.gen.ts` (`.gitignore` line 42) is also excluded" and then says "Every grep hit counts, comments included: a comment or string anywhere in `src/` (outside the two excluded route declarations and `routeTree.gen.ts`) that matches either pattern fails the criterion." The two formulations disagree about whether `/api/v1/` paths are excluded. The "References" section says `/api/v1/` paths are excluded; the acceptance criterion omits that exclusion. If `/api/v1/` paths contain `settings/github` (e.g. API endpoint strings), the acceptance criterion as written would fail the build while the "References" section says it passes. This must be resolved: either the criterion explicitly excludes `/api/v1/` paths, or the "References" section must drop that exclusion and explain why no `/api/v1/` path would match.

**[B-3]** The "Connections page loading" decision requires per-platform `useQuery` keyed per platform plus `InlineError onRetry={refetch}`, but the shown excerpt of `api-tokens-section.tsx` (lines 228-241) shows `TokenListSection` using a single `useQuery` for the entire list, not a per-platform pattern. The brief asserts this is "the existing component-level pattern" and cites `api-tokens-section.tsx:229-241` as evidence, but the excerpt shows exactly one `useQuery` and one `InlineError` — there is no per-item or per-platform query keying visible. If the claimed pattern does not exist as described, the implementer cannot follow it, and the test that asserts "Retry re-runs only that load" may be testing an implementation that has no precedent to match. The brief must either show the source that demonstrates per-platform query keying exists elsewhere, or specify the pattern explicitly without claiming it is an existing one.

**[B-4]** The `SecretDialog` extraction contract says the extracted component's default `closeButtonText` is `I've stored it, close`, but the acceptance criterion for the post-create hook says `closeButtonText?` is optional in `PostCreateReveal` and "defaults to the dialog's own button text when absent." The shown excerpt (`api-tokens-section.tsx` line 219) hard-codes `I've stored it, close` inside `SecretDialog`. The brief does not show how the extracted component will handle a `closeButtonText` prop alongside the hard-coded string, nor whether `CreateTokenSection` will pass it explicitly or rely on the default. If the extraction keeps the hard-coded string as the default and adds an optional override, the contract is implementable; if it requires `CreateTokenSection` to pass the string explicitly, that changes the shown call site (lines 170-173). The brief must clarify the exact prop interface of the extracted `SecretDialog` and how `CreateTokenSection` passes the close-button text.

**[B-5]** The Target-kind contract requires `load(context, signal)` to be "async and owned by the kind," with `targets-row.tsx` keeping "one load state per kind," but the acceptance criterion for the create-button gate says availability is "judged from the loaded `context` (installation count), never from whether a lazy repository or runner-group list has loaded." These two statements conflict: if load state is per-kind and lazy lists are loaded through the kind's `load`, then availability *is* partly a function of load state (a kind cannot be available before its load resolves). The brief then says the gate uses `options.installations.length`, not the lazy list state. This means the gate is not actually derived from the standalonerule's target kinds at all — it is derived from a separate `context` field (`options.installations`) that `targets.ts` must know about. The Target-kind contract does not specify how `targets.ts` receives the installation count; it only says `load(context, signal)` uses "the already-loaded data (`getCreateRunnerPoolOptions()` result...)". The brief must specify exactly what `context` contains for the gate, and whether `targets.ts`'s `anyStandaloneKindAvailable(context)` reads it from the same `context` object that the picker's load function receives, or from a separate source.

**[B-6]** The acceptance criterion for payload-equality says "Every case drives the rendered form (not `targets.ts` or a descriptor partial alone) and compares the `data` argument recorded at `createRunnerPoolAction` / `updateRunnerPoolAction`." The Target-kind contract also says "The builder calls **every** registered descriptor's partial, whether or not that platform has a selected target." The brief does not specify the injection point for the new-pool and pool-settings forms' registry access. If a test-only descriptor is needed for the picker's mixing rules (the acceptance criteria require testing Bitbucket's non-standalone behavior), the forms must be able to render a registry that includes a test descriptor. ### WARN findings

**[W-1]** The acceptance criterion for the grep over `src/` states "a new comment such as `redirects /settings/integrations` must not be written outside the two redirect-only files." This is a reasonable constraint, but it creates a surprising authoring rule: the implementer must avoid writing documentation that names the old routes. If a developer wants to explain why a link was repointed, they cannot mention the old path in a comment without failing CI. The brief should consider whether this is intentional — if the goal is to prevent accidental links, perhaps a different mechanism (e.g. a lint rule) would be more maintainable than an absolute grep prohibition.

**[W-2]** The "Connections page loading" decision says "`Promise.allSettled` is not used" and "GitHub rows are derived from the `/settings` page data props (`page.data.installations`) — no fetch, no Retry for GitHub." The brief does not specify how `ConnectionsSection` distinguishes a platform with a list binding (Bitbucket, fetchable, retryable) from one without (GitHub, derived). If the descriptor's list binding is optional and GitHub supplies a *binding* that reads from `page.data`, then GitHub *does* have a list binding (it just doesn't fetch). The brief must clarify: does "list binding" mean "fetch function" or "function returning items"? The acceptance criterion for partial load failure ("one platform's list binding rejects") suggests list bindings can reject, but the GitHub derived binding cannot reject. This creates ambiguity about whether GitHub is a descriptor with a list binding that happens to be synchronous, or a special case in `connections-section.tsx` (which would violate the "no platform-specific code" requirement).

**[W-3]** The Target-kind contract mandates "The builder calls **every** registered descriptor's partial, whether or not that platform has a selected target, because today's payload always carries `bitbucketConnectionIds` (`[]` when none)." This means the neutral builder iterates `platforms` and calls `toCreatePayload`/`toUpdatePayload` on every descriptor. If a future platform (e.g. GitLab) adds a partial, the builder will call it for every pool submission, even if GitLab is not selected. This may be intended (to preserve "always send `bitbucketConnectionIds: []`"), but it couples the builder to every descriptor's willingness to return an empty partial. If a future descriptor's `toCreatePayload` throws when its platform has no selection, the builder breaks. The brief should specify that partials must be total functions (never throw) and must return an appropriate empty/default partial when their platform is not selected.

**[W-4]** The acceptance criterion requiring "no `bitbucket`/`github` branching in shared rows" is asserted as testable, but the brief does not enumerate what counts as "shared rows" beyond the ones listed in "Current platform-branching sites in shared rows." The criterion says "no `bitbucket`/`github` branching" but does not define whether helper functions or `targets.ts` functions that branch on `kindId` are exceptions. The Target-kind contract itself uses kind ids (`github.repository`, `github.runner-group`) to branch on behavior (e.g. `standalone: true` vs `false`), so some branching on platform/kind must remain somewhere. The brief must clarify: does the criterion mean no *JSX* branching on `bitbucket`/`github` in shared rows, or no *any* platform-specific conditional in `runner-pools.new.tsx` / `runner-pools.$poolId.settings.tsx` (including calls to `targets.ts` that behave differently per kind)?

**[W-5]** The brief says "GitHub and Bitbucket only. Do not add a GitLab descriptor (that is #141)." But the acceptance criterion for the post-create hook requires "a test-only descriptor whose post-create hook returns a value." The test-only descriptor is not a production descriptor, so it doesn't violate the "GitHub and Bitbucket only" scope. However, the Forward-compat note asks the survey to confirm that `#141` can add GitLab "without touching the page, picker or options components." The brief does not require a test that actually *simulates* a GitLab descriptor in the picker to prove the descriptor contract suffices. The acceptance criteria only test `postCreate` with a fixture descriptor; they do not test that a new descriptor can drive the Targets row or Platform options section unchanged. The Forward-compat note's claim is therefore untested. The brief should either add a test that renders the Targets row with a test-only descriptor that has GitLab-like target kinds (proving the contract suffices), or the Forward-compat note should be demoted to a design statement rather than an acceptance criterion.

### NIT findings

**[NIT-1]** The brief says "No API, database or OpenAPI schema change" but also says "the frontend zod module `src/features/runner-pools/schemas.ts` MAY be edited to export existing rules for reuse, without changing what it accepts or rejects." This is a subtle but important distinction (frontend schema vs API schema). The brief could more explicitly define "schema" in the scope to avoid confusion: the OpenAPI schema is off-limits, but the frontend zod schema is in-scope for refactoring exports only.

**[NIT-2]** The acceptance criterion for the create-button gate says "availability is judged from the loaded `context` (installation count)." The word "loaded" may mislead: installations are loaded by `getCreateRunnerPoolOptions()`, which is a synchronous options fetch or a pre-fetched context. If the context is "already-loaded data" (as the Target-kind contract says), then "loaded" means "already fetched before the form renders," not "lazy-loaded on demand." The brief could clarify this to avoid the misreading that the gate depends on a loading state.

**[NIT-3]** The excerpt from `settings.integrations.tsx` lines 11-17 shows an import statement spanning lines 11-17. The brief's grep analysis says "line 17 is a module specifier, not a `Link`/`redirect` target." That is correct, but the excerpt is misleadingly bounded: it starts at line 11, which is the closing of an import statement, without showing the opening line 10. The analysis is sound, but the reader has to trust the claim that line 17 is an import specifier.
