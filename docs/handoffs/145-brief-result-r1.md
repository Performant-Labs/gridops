## Brief Review (Round 1)

### BLOCK findings

**[B-1]** The acceptance criterion for the post-create reveal dialog uses a test-only descriptor, but the descriptor contract's `post-create hook` return type is unspecified. The brief says the hook "returns something to show once — e.g. a webhook secret" and the acceptance criterion says "driven by a test-only descriptor whose post-create hook returns a value: the value is shown once after create and not again after the dialog closes." However, the brief never defines what type the hook returns, how the value flows from the plain async create call into the `SecretDialog` component, or whether the `SecretDialog` extraction (per the Reuse map) accepts arbitrary values or only strings. The Reuse map specifies `SecretDialog` gets generic props (`open`/`value`, title, description, secret label, optional details slot, close-button text, `onClose`, `onClosed`), but the descriptor type's post-create hook field is described only as "an optional hook that returns something to show once." Without a concrete type contract (e.g. `{ title: string; description: string; secretLabel: string; value: string; details?: Record<string, string> }`), an implementer cannot write the test-only descriptor, T cannot write a test that compiles, and the criterion is untestable as stated — the test must know the shape of what the hook returns to assert it appears in the dialog. Must specify the exact return type of the post-create hook in the descriptor contract.

**[B-2]** The acceptance criterion for redirects requires both a Vitest assertion and a grep showing no remaining `"/settings/github"` or `"/settings/integrations"` strings "outside the two redirect-only route files." But the brief itself identifies three route files that become redirect-only: `settings.github.tsx`, `settings.integrations.tsx`, and `_app/platform-connections.tsx`. The criterion says "two redirect-only route files," which is inconsistent with the brief's own Required design 2, which says "/settings/integrations, /settings/github and /platform-connections redirect (replace) to it" and that `_app/platform-connections.tsx` must be updated in place. If `_app/platform-connections.tsx` still contains the string `"/settings/integrations"` after the change (it currently targets that route), the grep as literally stated would flag it, but it would be a redirect-only route file — creating a contradiction. Must clarify whether the grep excludes all three redirect-only route files or whether `_app/platform-connections.tsx` must have its target string changed to `/settings/connections` before the grep passes.

**[B-3]** The acceptance criterion "No in-app link or redirect targets a redirecting route" lists the `settings.index.tsx` `?appError=` redirect as something that must "point directly at `/settings/connections`," but the brief does not specify what happens to the `appError` query parameter. The current code (`settings.index.tsx` line 10) redirects `?appError=` to `/settings/github` — implicitly preserving the query parameter. If the new redirect points to `/settings/connections`, the `appError` query parameter must be preserved for the GitHub App section to display the error (the brief says the GitHub App setup "may stay as a section on this page"). The brief does not state whether the `appError` handling moves to `/settings/connections` or is dropped. This is a functional gap: the criterion demands the redirect change but does not specify the error-passing behavior, making the criterion incomplete. Must specify whether `appError` is preserved on the new redirect and how the Connections page consumes it.

**[B-4]** The brief requires the new-pool form's create button disabled state to derive from the "standalone-target gate in `targets.ts`" equal to today's value (`options.installations.length === 0`), but the Target-kind contract's `standalone` field is only described for Bitbucket ("Bitbucket workspace is not standalone — it requires a GitHub target"). It is never stated which kind is `standalone`. The contract says the create button is disabled "when no standalone kind has any loadable target," but if the GitHub repository kind and GitHub runner-group kind are mutually exclusive (`excludes`), and Bitbucket is not standalone, then the standalone gate must identify GitHub repository and/or GitHub runner-group as standalone. The brief does not declare a `standalone: true` flag on either GitHub kind. Without that declaration, the equality to `options.installations.length === 0` is underivable from the stated contract, and the acceptance criterion (every existing flow still works) is untestable for the disabled-button behavior. Must declare which target kinds are `standalone` and show that the derived disabled state equals today's for all GitHub/Bitbucket selections.

**[B-5]** The brief requires payload equality for the pool-settings organization-pool save, but the Target-kind contract and the frozen old-form constants depend on `priorityRepositoryIds` and `priorityWaitMinutes` being "undefined" for organization pools. The verified excerpt from `runner-pools.$poolId.settings.tsx` lines 122-144 shows these fields are set with ternary expressions yielding `undefined` for organization pools. However, the brief's Reuse map says the update context must carry "the pool-settings form values the GitHub update partial needs: `priorityRepositoryIds` and `priorityWaitMinutes` (and `runnerGroupId`)," and the GitHub update partial sends `repositoryIds`/`priorityRepositoryIds`/`priorityWaitMinutes` "only for repository pools (else `undefined`)." The frozen capture process (Phase-5 sequencing) requires T to capture the old form's `data` object before any `src/` change. But the old pool-settings form has no Bitbucket workspaces control (verified excerpt), so the `bitbucketConnectionIds` field is absent from the old update payload — the brief correctly says "update omits `installationId`, `scope` and `bitbucketConnectionIds`." This is consistent. However, the acceptance criterion's `toEqual` comparison operates on the `data` object passed to `updateRunnerPoolAction`, which includes `poolId` (stripped by the action function per `runner-pools.functions.ts` line 133). The brief says "`poolId` is part of the compared `data` object." The new form must therefore include `poolId` in the `data` it passes, even though it is stripped before the API call. This is specified, but the brief does not state where the new form gets the pool id in the settings context — it is available from the route (`pool.id`), but the descriptor's `toUpdatePayload(selection, pool, context)` signature must carry it. The contract says the update partials return "partials" merged by a neutral builder with shared rows, but `poolId` is not a shared row field nor a target field. Must specify whether `poolId` is injected by the neutral builder, the form, or the GitHub update partial, so the equality comparison can be reproduced. Without that, the payload-equality criterion is underspecified for the update path.

### WARN findings

**[W-1]** The brief requires the `SecretDialog` extraction to keep `tests/api-tokens-section.test.ts` "green unmodified in intent," but the extraction changes the dialog's props. The existing `SecretDialog` is a private function in `api-tokens-section.tsx` (shown at lines 186-226) with props `{ revealed, onClose, onClosed }` where `revealed` is a `RevealedToken | null` carrying `{ secret, token }`. The generic extraction changes it to `{ open, value, title, description, secretLabel, details, closeButtonText, onClose, onClosed }`. The existing test at `tests/api-tokens-section.test.ts` (test name "shows the secret once, ignores Escape, and forgets it on close") likely interacts with the DOM through the API-tokens section, so it may not directly import `SecretDialog`. But if the test does import or render the component directly (not shown in the excerpts), it will break. The brief says T must update `tests/runner-pool-tart-image.test.ts` but only says `tests/api-tokens-section.test.ts` "must keep passing after the SecretDialog extraction." If the test renders `TokenListSection` and asserts the dialog closes, the test should pass through the wrapper. Recommendation: T should verify whether `api-tokens-section.test.ts` imports `SecretDialog` directly or drives it through `TokenListSection`, and if the former, update it in the RED phase to use the extracted component's new interface.

**[W-2]** The brief's acceptance criterion for redirects requires a grep over `src/` showing no `"/settings/github"` or `"/settings/integrations"` strings outside the redirect-only route files. The "References to the redirecting routes" section lists `_app/webhooks.tsx:83` as one of the files that must be repointed. However, `webhooks.tsx` line 83 is shown in the source excerpt, and the link text is "GitHub settings" — its `to` prop is `"/settings/github"`. After repointing to `/settings/connections`, the link text should probably change too ("Connections" or similar), but the acceptance criterion only enforces the href, not the visible text. Recommendation: add a criterion or note that the visible link text should be updated to match the new page name, otherwise the UI will show "GitHub settings" leading to a Connections page, which is confusing.

**[W-3]** The brief's reuse map says the GitHub App section "moves verbatim" from `settings.github.tsx` to `github-app-section.tsx`, but it also says the route "reads `getRouteApi("/settings").useLoaderData()`" and passes `page.data` as props, with the section never calling `getRouteApi` itself. This is a behavioral change: the current `settings.github.tsx` calls `settingsRoute.useLoaderData()` inside the component. The move requires extracting the component's data dependencies into props. While the brief explicitly specifies this (lines 20-30 show the current pattern), the "verbatim" wording is misleading — the section will need to receive `configuration`, `githubApp`, `installations`, `user` as props, which is a structural change even if the JSX is moved verbatim. Recommendation: clarify in the handoff that "verbatim" refers to the JSX and action calls, not the data-access pattern.

**[W-4]** The brief requires `runner-pools.$poolId.settings.tsx` to show Bitbucket targets as "locked display-only chips," but the current settings form has no Bitbucket workspaces picker (verified excerpt). This means the settings form must now display Bitbucket connection information read from `pool.bitbucketConnectionIds` and map those ids to workspace names. The brief does not specify where the workspace names come from — the pool detail (`RunnerPoolDetail`) may or may not include `bitbucketConnectionIds` with names, or the form may need to load `getBitbucketConnections()` to resolve the ids. The Target-kind contract's `load(context, signal)` says context "carries the already-loaded data ... or the pool detail on settings," but the pool detail schema is not shown. Recommendation: verify that `RunnerPoolDetail` includes enough information to display Bitbucket workspace names on the settings page, or specify the lookup path for resolving `bitbucketConnectionIds` to labels.
