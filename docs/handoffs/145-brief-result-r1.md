## Brief Review (Round 1)

### BLOCK findings

**[B-1]** The acceptance criterion "No in-app link or redirect targets a redirecting route" defines its grep exclusion "by pattern, not by line number" for the two redirect-only files, but the exclusion regex is anchored to a verbatim line format that can only match if the file's route declaration appears on the exact text `export const Route = createFileRoute("/settings/github")({` with no whitespace variation. The verified excerpts show this is true today (settings.github.tsx line 20 verbatim: `export const Route = createFileRoute("/settings/github")({`), but the criterion's own language — "after this story both files are redirect-only and their line numbers will change, which does not affect the check" — does not account for the implementer reformatting (e.g. adding a space before `({`, splitting across lines, or a code formatter wrapping it). A format change to the route declaration would cause the grep to print a hit and fail the criterion even though the only string in the file is the legitimate route declaration. The criterion must either (a) pin the exact line format as an invariant ("the declaration line must remain this exact text"), or (b) relax the exclusion to match any line in those two files matching `createFileRoute\("/settings/(github|integrations)"\)`, so formatting changes don't spuriously fail.

**[B-2]** The post-create reveal acceptance criterion requires the test-only descriptor's `postCreate` to return an object typed as `PostCreateReveal` imported from `src/features/platform-connections/types.ts`, and states "the test file must typecheck against that `types.ts` declaration (`npm run typecheck`)". But `src/features/platform-connections/types.ts` does not exist yet — it is created by this story, listed under "Not found (created by this story)" in every source-material pass. The criterion is therefore only checkable after F writes `types.ts`, which is fine for acceptance but vacuous as a brief-gate criterion: at brief-gate time there is no declaration to typecheck against, and the criterion gives no independent shape for `PostCreateReveal` beyond the prose in the "Post-create hook contract" section (which does specify `{ title: string; description: string; secretLabel: string; value: string; details?: ReactNode; closeButtonText?: string }`). The criterion is testable once `types.ts` exists, so this is not a BLOCK in the sense of a contradiction — but the criterion as written depends on a file that is itself part of the unbuilt implementation, and the brief gives no acceptance check to ensure `types.ts` actually declares the contract the test imports. Fix: state that `types.ts` must declare `PostCreateReveal` with the exact fields in the "Post-create hook contract" section, and make that a separate testable criterion (e.g. a type-level assertion or a `describe` that TypeScript compilation enforces).

**[B-3]** The acceptance criterion for payload-equality tests defers verification to "Phase 5" because the frozen constants do not exist at brief-gate time. The brief acknowledges this ("the frozen constants do not exist at brief-gate time and this brief deliberately does not contain their values"). But the criterion as written is still listed as a round-1 acceptance criterion, and its verifiability at this gate is impossible: no reviewer at brief-gate can check derivation rules against constants that don't exist, and the criterion itself says "A reviewer at the brief gate checks the derivation rules, not constant values." That statement is correct — but the derivation rules are described in prose ("T captures them from the old forms at commit `5550cf5`"), and the brief gives no testable rule for *whether the capture was done correctly* beyond a hand cross-check against excerpts that the brief itself admits don't show the concrete shared-row values. This is a sequencing gate, not an acceptance criterion: the brief should either (a) remove it from the acceptance list and record it as a sequencing/handoff requirement, or (b) state a testable invariant (e.g. "T's handoff note records `git diff 5550cf5 <T's last commit> -- src` as empty, and the test file's constants include commit/line comments naming `5550cf5`") and make that invariant the acceptance check. As written, the criterion is unverifiable at brief-gate and relies on a future capture step that cannot be independently checked without the captured constants.

### WARN findings

**[W-1]** The rejection of `toStrictEqual` in favor of `toEqual` for payload-equality tests is justified (JSON.stringify drops `undefined` keys), but the criterion does not state whether the frozen constants themselves contain `undefined` values as object properties or omit them. If the constants are hand-written by T with `repositoryIds: undefined` for organization pools (matching the old form's literal code), `toEqual` works; but `toEqual` treats `{ a: undefined }` and `{}` as equal, so there is a risk the test could pass even if the new code sends a key the old code didn't (e.g. `scope: undefined`). The criterion says "a mismatch is fixed in the implementation, not in the constant," but a test that ignores `undefined`-valued keys can't catch an implementation that adds a `scope: undefined`. Recommendation: state explicitly that the frozen constants must include the literal old-form keys exactly as they appear in the old-form code (so a missing key in new code would fail `toEqual`, and an added `undefined` key would not mask a real difference).

**[W-2]** The acceptance criterion for the create-button gate requires `anyStandaloneKindAvailable(context)` to return true when "some registered kind with `standalone: true` returns true from its `available(context)`." But the criterion does not test the case where a future descriptor is registered with a custom `available` that throws or returns a non-boolean. The type contract says it returns `boolean` synchronously, so this is nominally type-safe, but a runtime error in a third descriptor's `available` would crash the form. For the forward-compat claim (#141 adds a descriptor without touching this logic), it might be worth adding a test that a descriptor's `available` throwing does not break the gate (e.g. catches and treats as false). Not required for GitHub/Bitbucket, but the forward-compat criterion implies robustness.

**[W-3]** The "partial load failure" acceptance criterion requires the test to render `ConnectionsSection` with descriptors containing "fetching list bindings (one rejecting, one resolving)" and assert per-platform error + Retry. But the criterion also says "it also passes page data with ≥1 installation and the production GitHub descriptor, and asserts the GitHub rows render with no error or Retry control of their own." This mixes two concerns: the test is both a generic test of the component's per-platform load isolation and a regression test of the production GitHub descriptor's page-derived binding. If the former uses test-only descriptors, the test does not validate that the production Bitbucket descriptor's `getBitbucketConnections()` actually rejects when its fetch fails (it would, but that's an inference). Consider splitting into two tests: one with test-only descriptors proving the isolation, and one with the production descriptors stubbing `fetch` to fail for Bitbucket and asserting the production error path. The current combined criterion is weaker than it looks.

**[W-4]** The forward-compat acceptance criterion (test-only third descriptor rendering in `TargetsRow` and `PlatformOptionsSection`) asserts "with no change to `targets-row.tsx`, `platform-options-section.tsx` or `connections-section.tsx` beyond what the GitHub/Bitbucket descriptors already need." This is circular: the test proves those components render a third descriptor's data, but the phrase "beyond what the GitHub/Bitbucket descriptors already need" assumes the components were written correctly for two descriptors, which is what the rest of the brief specifies but doesn't independently verify. The circularity is harmless (the test does exercise a third descriptor), but the criterion should simply say "with no platform-specific code in those three files" and rely on a separate lint or grep assertion for that property.

### NIT findings

**[NIT-1]** The brief uses both `docs/handoffs/145/survey.md` and `docs/handoffs/145-brief.md` (with and without a hyphen) in different places. The "Source material read" section lists both, and the "Handoff locations" section says the survey is `docs/handoffs/145/survey.md`. Confirm the intended path is consistently `docs/handoffs/145/survey.md` (the run directory), not a stray `docs/handoffs/145-brief.md`.

**[NIT-2]** The grep exclusion in the acceptance criterion uses the shell command `grep -rn -e "settings/github" -e "settings/integrations" src --exclude=routeTree.gen.ts | grep -v -E '^src/routes/settings\.(github|integrations)\.tsx:[0-9]+:export const Route = createFileRoute\("/settings/(github|integrations)"\)\(\{$'`. The `--exclude=routeTree.gen.ts` will exclude `src/routeTree.gen.ts` only if the current working directory is the repo root and the generated file is directly under `src/`. The brief notes the file is gitignored and "not found in the worktree," so the exclusion may be moot in CI, but if the file exists during a local run the exclusion works only for the exact basename. The command should use `--exclude=src/routeTree.gen.ts` or run from a fixed root to be unambiguous.

**[NIT-3]** The criterion requiring test-only fixtures "under `tests/fixtures/`" and the payload-equality constants "in a test file" are clear, but the brief doesn't specify whether the capture harness (driving the old form at `5550cf5`) is also under `tests/` and later removed, or lives outside the test glob pattern. Since the harness "is not committed as a collected test," it should be explicitly stated it is a temporary script outside `tests/**/*.test.ts` (or under `docs/handoffs/145/` as a note), to avoid accidental Vitest collection.
