#159 Pool list and pool detail: the destination comes from the platform registry

No new page, nav item or control. Two existing surfaces change how they work out a pool's destination: the destination cell of a pool-list row (PoolRow) and the Destination group of the pool detail's properties panel. GitHub and Bitbucket pools must look exactly as today (frames A and C are the unchanged baseline, drawn from the current source). A GitLab pool stops showing the installation's GitHub account and shows its GitLab connections instead (frames B and D). Exact copy is highlighted yellow. Icons are Unicode stand-ins (◆ for the GitHub avatar square, GL for the GitLab platform icon, which in the build is the registry descriptor's icon, lucide Gitlab as in gitlab.tsx); nothing here is final visuals.

The "GitLab" badge in the middle cluster is the existing provider/label badge area and is drawn only to identify the case; this change does not add it.
  1. 1One connection: its name, exactly as stored (Acme / web). Two or more: N connections in the cell and all names joined with ", " in the cell's title (hover shows it; drawn as the dark tooltip).
  2. 2Leading mark is the GitLab platform icon (the descriptor's icon), 16px, in the avatar's slot. No GitHub avatar for any GitLab row; githubAvatar is no longer referenced by the route.
  3. 3Empty or absent gitlabConnections (a pool with none, or an older server that omits the field): neutral GitLab with the same icon, title "GitLab". Never the installation's GitHub account.
  4. 4Connection with an empty name (partial data): the cell uses baseUrl/scopePath in its place; if both are missing too, a single such connection falls to the neutral GitLab (with several connections the count is unaffected).
  5. 5Unknown scope (a scope no descriptor owns): the registry's neutral fallback, never throws. Cell is a dash — with a neutral placeholder square (no GitHub avatar, no platform icon), title "Unknown destination".
  6. 6Cell width, truncation and the hidden xl:flex responsive rule are unchanged. The API now sends gitlabConnections on each list item (one batched query), which is what feeds notes 1 to 4.

  1. 1Scope row: GitLab (the platform's proper label, not the capitalised raw value "Gitlab" seen today).
  2. 2Connections from RunnerPoolDetail.gitlabConnections, in the server's order, one two-line item per connection in the same chip style as the repository list: line 1 the name, line 2 baseUrl/scopePath as the detail (muted, truncates; the whole item's title carries the full text). No label row above them, as the repository list has none.
  3. 3No Account row, no GitHub avatar, no Runner group row for a GitLab pool (that "#1" was the installation's meaningless runner group).
  4. 4No connections / field absent (older server): Scope GitLab then a muted No connections listed line. Never the installation's GitHub account.
  5. 5Partial connection data: an absent baseUrl or scopePath shows only the part present (no stray "/"); if both are absent line 2 is omitted. An empty name shows the second line's text as the name and omits line 2.
  6. 6Unknown scope: Scope row Unknown and nothing else in the group. Never throws, no GitHub avatar. The raw scope string is not echoed.
  7. 7All connections are listed (no "Show N more" toggle); the pool form's Targets picker already limits how many a pool can have in practice. Display only: nothing here is editable or links out.
