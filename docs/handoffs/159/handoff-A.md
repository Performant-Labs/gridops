## Summary
PASS. The plan extends the right objects:
- It adds pool hooks to the existing `PlatformDescriptor` contract.
- It adds a `platformForPool` resolver beside `getPlatform` and `platformForDeliveryId` in `registry.tsx`.
- It adds one batched helper beside `pool_gitlab_connections` in `resources/gitlab.rs`.

It builds no parallel path. Moving `RepositoryList` into `github.tsx` is a refactor-to-extend that the brief names, not drift.

There are five warns, and none blocks:
- how to group the new hooks so the contract stays total;
- where the unknown-scope fallback copy lives;
- how the batched SQL stays in step with the detail's SQL, and where the Rust test goes;
- how to extend the source-guard test without a blanket `/github/i` check;
- a sibling of this defect, the runner row (plus the dashboard scope label), that is still not recorded anywhere.

**Checked and consistent (no finding):**
- **Registry resolver.** `platformForPool(pool)` mirrors `platformForDeliveryId` (`registry.tsx:45-47`).
  - A scope-to-descriptor lookup over `platforms` names no platform, so the "registry names GitLab only in its import, its array entry and comments" test (`platform-neutral-source.test.ts:123-134`) keeps passing.
  - The scopes are disjoint, so the registry order does not matter.
- **Scope ownership as a declaration.** This matches the contract's "Declared by the descriptor, never inferred from its id" rule (`types.ts:33-37`). It also makes explicit what `github.tsx:248` and `gitlab.tsx:352, :361` already imply.
  - Bitbucket declaring no scope matches `bitbucket.tsx:43-46`: a workspace rides on a GitHub target's pool.
- **Where the code lives.** GitHub's hooks and `RepositoryList` go in `github.tsx`, which already holds JSX components such as `InstallationAside` (`:157-161`). GitLab's go in `gitlab.tsx`.
  - Importing `PropertyRow` from `~/components/page` follows the existing direction: `components/page.tsx` imports nothing from features, and feature modules such as `runner-pools/targets-row.tsx` already import it.
- **Wire type.** `gitlabConnections?: GitlabPoolConnection[]` on `RunnerPool` makes `operations.functions.ts` take a type-only import from `~/features/runner-pools/runner-pools.functions`.
  - This is the same direction as its existing `~/features/runner-pools/builtin-host` type import (`operations.functions.ts:2`).
  - `runner-pools.functions.ts` imports nothing from `operations`, so there is no cycle.
  - `operations.functions.ts` is already on the GitLab allowlist (`platform-neutral-source.test.ts:112`).
  - Making the field optional matches `RunnerPoolDetail.gitlabConnections?` (`runner-pools.functions.ts:69`) and avoids churn in test fixtures.
- **`readOnlySummary` is left alone.** The brief justifies the new hooks in writing:
  - `readOnlySummary` takes `RunnerPoolDetail` and returns one summary per platform with targets (`targets.ts:146-152`), so a Bitbucket pool yields two summaries.
  - The destination is owner-only, and its text differs ("N repositories" only when there is more than one repository).
  - These are deliberate, separate semantics, not duplication.
- **Coexistence.** No live worktree branch changes `runner_pools` in `resources.rs`, `resources/gitlab.rs`'s pool helpers, the two routes, or the descriptor and registry files.
  - `fix/134-exclusive-pools` touches only `PoolAccess`, `provision`, `pool_access` and `diagnose_queued_job`.
  - `claude/gitlab-138-followup` touches only the visibility of `credentials`.
  - The #141 branch's overlap is already on master (99375fb).
