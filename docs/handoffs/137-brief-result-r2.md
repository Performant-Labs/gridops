## Brief Review (Round 1)

### BLOCK findings

**[B-1]** [new, correctness] The `GitlabRunnerMaterial` field order test is specified as byte-for-byte deterministic solely on the claim that "serde's derived `Serialize` for an internally tagged enum writes the tag (`kind`) first and then the variant's fields in their declaration order, every time." This is stated as fact in A-2, but the prompt shows no serde source excerpt or documentation supporting that serialization order is guaranteed by the derive macro. The brief itself acknowledges the risk by requiring a test to "catch it" if field order changes: "reordering the fields is a contract change, and the byte-for-byte test is there to catch it." That is circular — the test asserts a literal that the implementation itself generates. If the derived serializer's order is not actually guaranteed by serde's contract (as opposed to being an observed behavior in a scratch crate), the test could fail on a serde patch release with no way to fix it except hand-writing `Serialize`. The brief must either hand-implement `Serialize` for `GitlabRunnerMaterial` to make the byte order part of the contract, or drop the byte-for-byte equality criterion in favor of structural equivalence (deserialize and compare fields, or compare as `serde_json::Value`).

**[B-2]** [new, completeness] The brief claims `Debug` for `GitlabRunnerMaterial` "is implemented by hand and prints `token: "[redacted]"`." It does not specify whether that hand-written `Debug` applies to the enum as a whole, the variant, or a newtype. If the enum contains `url` and `wait_timeout_seconds`, the `Debug` output must include those non-secret fields while redacting only `token`. The brief says the test asserts `format!("{:?}")` doesn't contain the token, but it does not pin what the `Debug` output does contain. An implementation could satisfy the test by printing an empty string for the whole struct, which would make debugging impossible for wave-1 consumers (#139, #147, #142). Specify the exact `Debug` output format, including that `url` and `wait_timeout_seconds` are printed in full, or at minimum that `url` is present.

**[B-3]** [new, completeness] The `GitlabRunnerMaterial` test that pins "a payload with an extra field is rejected" uses `deny_unknown_fields` on the internally tagged enum. The prompt asserts this was checked against serde 1.0.229 in a scratch crate, but does not show the serde source or the scratch crate output. `deny_unknown_fields` with internally tagged enums has historically been unreliable across serde versions, because the deserializer for an internally tagged enum first deserializes into a `TaggedContent` buffer that may not reject unknown fields in the same way as a struct. This is a well-documented serde limitation (serde issue #1706 and related). The brief's own evidence is an assertion of a scratch-crate result, not a source excerpt. If the behavior is real, it must be pinned with a test, but the test alone doesn't prove it will hold on every serde version in the lockfile's range. Needs a serde documentation/source excerpt showing `deny_unknown_fields` is honored for internally tagged single-variant enums, or the contract must drop `deny_unknown_fields` and rely on a hand-written `Deserialize` that rejects extra fields explicitly. This is a completeness finding, not a correctness one, because the prompt does not contain the serde source needed to settle it; but it blocks because the contract depends on a behavior that is notoriously version-sensitive and the brief offers no mechanism to guarantee it.

**[B-4]** [new, completeness] The A-2 section requires a test that "a GitHub `PrepareEnvironment` fixture serializes byte for byte as it does on `master`" and that the "expected bytes are a string literal in the test: the output of `serde_json::to_string(&command(fixture())?)`, captured on `master` before any change in this issue." The brief does not provide the captured bytes. Without them, the test cannot be written except by running `master` during implementation and asserting the implementation equals itself — which would trivially pass regardless of whether `ExecutionConfiguration` was changed, because the implementation under test produces the bytes. The criterion is vacuous unless the expected literal is supplied in the brief itself, or unless the test compares against a checked-in golden file that this brief names and the diff gate later verifies is unchanged. State the exact expected JSON string for the GitHub `PrepareEnvironment` fixture, or name the golden file and its location.

**[B-5]** [new, completeness] The `ExecutionConfiguration::default()` field-set test in A-2 asserts the JSON is exactly `{"network":null,"session_id":null,"requires_interactive":false,"requires_docker_socket":false}`. The brief quotes `ExecutionConfiguration` as "today holds only `network`, `session_id`, `requires_interactive` and `requires_docker_socket`" but does not show the struct definition. If any of those fields has `skip_serializing_if` or a `Default` that differs from `null`/`false`, the test would fail. Conversely, if a field is added with `skip_serializing_if` and a non-default value in `ExecutionConfiguration::default()`, the byte test for `PrepareEnvironment` might still pass while the struct's field set changed — which the brief itself notes ("A field added with `skip_serializing_if` would leave the `PrepareEnvironment` byte test passing"). The `ExecutionConfiguration::default()` test is meant to catch that, but its expected literal is only correct if the current defaults are exactly as stated. The brief should quote the `ExecutionConfiguration` struct definition verbatim, including any `serde` attributes and the `Default` impl, so the test's expected literal is verifiable against the shown source.

**[B-6]** [new, completeness] The A-3 section pins `GitLabError::RateLimited { retry_after: Option<Duration> }` and says `retry_after` is "taken from `Retry-After`." The brief does not specify the parsing rule for `Retry-After`: the header can be an integer number of seconds (`retry_after: Option<Duration::from_secs>`), an HTTP-date (`chrono` parse to `Duration` until that date), or absent (`None`). #146, which implements the real client, needs this rule to be part of the contract; otherwise two implementations (real and fake, or #146 and #148) may disagree on how to interpret the same header. State the exact parsing rule: integer seconds as `Duration::from_secs`, HTTP-date as the difference from `Date` header or local time, and absent header as `None`.

**[B-7]** [new, correctness] The A-3 `JobStatus` enum is pinned with `is_terminal(): true exactly for Success | Failed | Canceled | Skipped`, and the `gitlab_jobs_open_created_idx` in W-5/W-6 uses `WHERE status NOT IN ('success','failed','canceled','skipped')`. This implies `JobStatus::is_terminal()` and the index predicate are identical. But `JobStatus` includes `Manual` and `Scheduled`, which are not terminal by this definition. The brief says "a job is concluded exactly when `JobStatus::is_terminal()`" and that `Manual` and `Scheduled` are open. That is internally consistent, but it exposes a correctness hole in the real GitLab API: a `Manual` or `Scheduled` job is not "open" in the sense of needing a runner — it is waiting for a human action or a schedule. The brief explicitly defers this to #148 ("Whether #148 acts on an open `Manual` or `Scheduled` job is #148's behaviour"), but that means a job recorded as `Manual` stays in the open index indefinitely, even after it succeeds or is canceled through the UI, because the reconciler won't poll it. If the open index is intended to bound the reconciler's scan, leaving `Manual`/`Scheduled` open breaks that bound for projects with many manual jobs. The brief must state whether `Manual` and `Scheduled` are terminal for the purpose of the open index, or add a separate status predicate for "needs a runner" that excludes them. As written, the index includes them forever, which is a correctness defect in the contract.

**[B-8]** [new, completeness] R2-1 item 3 pins `GITLAB_EXIT_IDLE_EXPIRED: i32 = 75` and `GITLAB_EXIT_REGISTRATION_REFUSED: i32 = 77`, and says "#147 owns the copy in `provisioning.rs`, and #142 the copy in the VM image." The brief says the Tart agent gets "a copy, with a test that pins the values." But the manager (built-in Docker host) also needs the copy in `provisioning.rs` (#147's), and the brief says #147 owns that copy. However, the exit codes are used by the runner script, which #147 also owns. If the script exits with 75/77, but the manager's listing code and the Tart agent's listing code both need to map those codes to `"idle_expired"`/`"registration_refused"`, then the constants must be in a place both crates can use. The brief says `gridops-core/src/provisioning.rs` holds the constants, but `crates/gridops-tart-agent` has no `gridops-core` dependency (NV-7, and R2-1 item 3 says "The Tart agent can't depend on core, so it gets a copy"). So the copy in the Tart agent is by necessity, but the manager uses the core constant. The brief does not state that the manager's listing code (#147) must use the same integer values as the Tart agent's copy. If the manager uses `GITLAB_EXIT_IDLE_EXPIRED` from core (75) and the Tart agent has a literal `75` in its copy, a typo in either would break the contract. The brief should require a test in both crates that asserts the mapping from exit code to `exitReason` string, and that the manager's test and the Tart agent's test both pin the same three strings (`"completed"`, `"idle_expired"`, `"registration_refused"`). The current text only requires a test that pins the integer values, not the mapping.
