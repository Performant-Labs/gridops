## Brief Review (Round 1)

### BLOCK findings
**[B-1]** [new, correctness] The brief's contract section states that `ProvisionRunner` on master has "`gitlab_runner_token: Option<SecretString>`, wire `gitlabRunnerToken`, the secret `glrt-` token", but the brief's own verified excerpt of `main.rs` shows `gitlab_runner_token: Option<String>` on the wire struct, with the note that "the token field is a plain `Option<String>` … the GitLab path must not log, format or `Debug`-print it (the struct derives `Debug`)". Two parts of the brief disagree, and the shown excerpt is the evidence: the field is a plain `String`, not a `SecretString`. Because the brief also says the contract is "already on master; do not change it", the implementer will hit this contradiction immediately — the SecretString guarantees (no `Debug` leak, no accidental formatting) do not exist on the wire struct, and the derived `Debug` on `ProvisionRunner` is an active leak path the brief must call out as an obligation (e.g. a test that the request struct is never Debug-formatted on the GitLab path). The contract restatement must be corrected to match the shown excerpt, and the secret-handling requirements restated in terms of a plain `String` field whose value must never reach `Debug`/log/error output.

Evidence: tart source (`TartCLI`/exec command implementation) or upstream documentation of `tart exec` exit-status semantics, cited in the handoff.

Evidence: `gitlab-runner` source (e.g. `commands/run_single.go`, token/env handling) or its documentation, cited in the handoff.
**[NV-3]** `POST <url>/api/v4/runners/verify` returns 403 for an invalid or revoked `glrt-` token (only if the script uses verify). Evidence: GitLab `runners/verify` API documentation or rails source.

### WARN findings
**[W-1]** The brief notes that `ProvisionRunner` has no `deny_unknown_fields` and "no `registration_token` field, so a stray `registrationToken` key is ignored on deserialization rather than refused", while D9's contract says a GitLab request carries "no `jitConfig`, `registrationToken`, `bitbucket` or `bitbucketOauthClientSecret`". Validation refuses `jitConfig`/`bitbucket`/`bitbucketOauthClientSecret` but cannot detect `registrationToken` at all, and the contract is frozen. The brief should state explicitly that a stray `registrationToken` is silently ignored (not refused) so #139/#147 and reviewers don't expect a refusal, and ideally record it as a contract deviation for the epic table.
**[W-2]** Scope item 1 says the runner binary path is configured "e.g. `GRIDOPS_TART_GITLAB_RUNNER_BINARY` … validated with `valid_guest_path`", and the image script installs "into the guest at the default binary path" — but the default path value itself is never stated anywhere in the brief. The script, the agent default and the docs must agree on one concrete path; specify it (or explicitly defer the choice to the diff with a single named constant).

### NIT findings
**[NIT-1]** Done-when's exit-mapping test says "a GitHub/Bitbucket runner" lists no `exitReason`; TartRecord today has no platform field at all, so the test names platforms the record format doesn't yet distinguish — harmless, but the test wording should track the new platform field's actual values.
**[NIT-2]** The `verify`-based 77 path is specified to read the token "from stdin/a pipe, never argv" but the concrete mechanism (e.g. `curl --data @-` from a here-fed fd vs a pipe) is left open; naming one in the brief would pin the fake-`curl` test shape.

### Verdict
BLOCK — 1 blocking finding ([B-1]); the contract restatement's `SecretString` claim contradicts the shown master excerpt and must be corrected before implementation starts.
