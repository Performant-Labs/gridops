## Summary
BLOCK. The plan picks the right object to extend: one more `PlatformDescriptor` beside `bitbucket.tsx`, with the three generic contract gaps closed in `types.ts` and `connections-section.tsx`. It leaves out two changes that the code makes unavoidable.

1. **GitHub descriptor.** `github.tsx` treats every pool that is not `"repository"` as an organization pool. A `scope: "gitlab"` pool's settings form would get a GitHub runner-group chip that should not be there. That chip disables every GitLab option. `github.tsx` is not on the brief's list of files that may change.
2. **Pool wire fields.** The GitLab pool fields must go into `schemas.ts` and `runner-pools.functions.ts`, as Bitbucket's did and as the #145 survey said they would. The brief bans GitLab strings in the first file (except the tag rule) and does not list the second.

Both need a brief amendment, not a redesign.

**Checked and consistent (no finding):**
- **Descriptor module.** GitLab is one `PlatformDescriptor` in `gitlab.tsx`, registered in `registry.tsx`, with its API functions in `platform-connections.functions.ts`. This matches `bitbucket.tsx`. "A target option is a connection" matches `workspaceKind`. `offered` and `toUpdatePayload` branching on `pool.scope` inside the descriptor matches #145's rule that only a descriptor may test scope.
- **Reveal.** Gap 3 needs no component change. `SecretRevealDialog.details` is a `ReactNode`, `CopyButton` can sit inside it, and `github.tsx` already renders shared components in `describe`.
- **Runner link.** The runner row is already registry-driven (`runner-row.tsx:83-93`). Adding `"gitlab"` and three optional fields to `Runner` (`operations.functions.ts:49-50`) follows the `bitbucketRunnerUuid` precedent.
- **Coexistence.** No other local or remote branch changes `src/` or `tests/` against `origin/master`. #138's branch does not either.
