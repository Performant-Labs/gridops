## Summary
PASS. The plan builds no parallel path. It:
- tightens `verify_access` in place, so create, token replacement and Verify all get the rule through the one call they already share;
- keeps the API's existing `MissingScope` message;
- writes the new warning into the existing `runner_events` table through the reconciler's event helper;
- shows it in the existing `PoolEventTable`.

There are six warns, and none blocks. They settle choices the brief leaves open or gets slightly wrong. The main ones:
- the per-runner event belongs inside `gitlab_lifecycle::deregister`, the one function all four per-runner deletion paths call. The brief lists three of those four.
- writing `runner_id` needs a small extension of the shared event helper.
- the level must be `"warning"`. The API's `"warn"` shows as green.
- the dedup state must be read back from `runner_events`, as `record_provider_changes` does.

**Checked and consistent (no finding):**
- **Right object for the rule.** `verify_access` is the single seam: create (`resources/gitlab.rs:139`), token replacement (`:254`) and Verify (`:317`) all call it, so one change to the scope loop (`http.rs:313`) covers all three.
  - `gitlab_message` (`:797-813`) already formats `MissingScope` as "The GitLab access token is missing the {scope} scope."
  - The order `create_runner`, `manage_runner`, `read_api` keeps today's first-missing semantics.
  - `UnconfiguredGitLab` (`gridops-api/src/state.rs:52`) and `UnavailableGitLab` (`gitlab_poll.rs:436`) fail every call and need no change.
- **Comments to update** are the ones the brief names and no others: `http.rs:304` ("`api` grants both") and `gitlab_live.rs:5-6`. `mod.rs:226` ("for example `create_runner`") is still correct.
- **The sweep's fan-out is acceptable, but the brief's reason for it is not.** Runner rows are only soft-deleted: there is no `DELETE FROM runners` anywhere. They disappear only when their pool is deleted (cascade). The marker also carries the row's uuid, so the sweep often does have a row. Fanning out to every linked pool matches `record_provider_changes` ("every pool that may start runners with the provider"), so keep it. The code comment should give the real reason: the row and its pool may be gone, and one row per pool bounds the noise. It should not say "no runner row".
- **The API's operator-delete path** (`cleanup_gitlab_runner`, `resources/gitlab.rs:603-660`) already records its GitLab refusal in the "Runner deleted" event's message and metadata. It is not in Need 2, and leaving it alone is right. Its only defect is the `"warn"` level in finding 3.
- **UI.** No new component, column or control. `PoolEventTable` already renders the tone, the Runner column, expandable metadata and the narrow layout. `getRunnerPoolEvents` returns `runnerId` and `metadata` as they are.
- **Coexistence.** #172's branch (`claude/gitlab-172-pool-image-bb7d36`) and #173's (`claude/gitlab-173-tart-prep-164633`) touch none of the files this plan changes. #139, #141 and #143, which touched them, are on master.
