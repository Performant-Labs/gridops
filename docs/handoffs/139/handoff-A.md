## Summary

BLOCK, with 4 block findings and 5 warnings.

These parts of the plan fit the code:
- a `gitlab_lifecycle.rs` child module that imports from `super::`, as `fleet.rs` does;
- a `gitlab: Arc<dyn GitLabApi>` field next to `bitbucket`;
- per-call credentials read through `runtime_secret`;
- connection selection modelled on `next_bitbucket_connection`;
- the spec'd GitLab arms in `targets.rs` and `service.rs` (D6, D11).

Three parts can't be built as written within the brief's own boundaries:
1. **Orphan sweep.** The shipped `GitLabApi` can't list runners, so there is nothing to sweep with.
2. **Pool delete.** It runs entirely in the API, which #139 may not touch.
3. **"Same insert" rule.** It contradicts D1 on the fleet path.

The fourth block is about placement. The file list ("main.rs gets only the call sites") leaves out files that must be extended. Read literally, it pushes F toward a parallel GitLab provision/start/delete pipeline, which the Phase 7 gate would reject.
