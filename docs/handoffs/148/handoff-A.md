**Verdict:** BLOCK

## Summary

BLOCK, with 4 block findings and 4 warnings. The module placement is consistent with the code: the GitLab branch goes in `autoscaling.rs`, `gitlab_poll.rs` sits beside `fleet.rs` and `tart_lane.rs`, and the scale-down guard is left alone. Four parts of the plan don't fit:

1. **The poll runs in the wrong place.** The plan runs it inside the reconcile pass, and its `job` checks are unbounded. The code already moved its GitHub equivalent out of the pass, for a reason it documents.
2. **Two id spaces leak into GitHub views.** The plan sends GitLab jobs through public types whose ids are GitHub job ids and GitHub repository ids, and those ids are joined back to GitHub tables in `gridops-api` and in fleet placement. The plan also leaves the key open and limits the diff to files that can't fix that.
3. **The status mapping is left open where the code already answers it.** Counting `running` as demand double-counts against `runners.busy`. Counting `created`, `waiting_for_resource` and `preparing` breaks the scaler's ready-only tier.
4. **The tag-matching choice is open, but #139 has fixed the answer.** The rule must equal the tags #139 registers runners with, and one of the two "decide and document" answers lets the two disagree.
