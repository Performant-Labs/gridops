## Brief Review (Round 1)

### BLOCK findings

**[B-1]** The `gitlab_jobs` schema is internally inconsistent. The W-5/W-6 pinned table defines `id` as `text PRIMARY KEY NOT NULL`, but the original issue scope says `gitlab_jobs` has a "unique index on `(connection_id, job_id)`". A PRIMARY KEY on `id` plus a UNIQUE index on `(connection_id, job_id)` is coherent, but no column named `id` appears anywhere else in the brief (the `Job` struct in A-3 has no `id` field, and `tag_list` is the only JSON column). What is the semantic of `gitlab_jobs.id`? Is it a UUID? A composite of connection and job? This must be specified or no implementer can write the INSERT in #140 or the SELECT in #148. Fix: specify the type and source of `id` (e.g. "UUID generated by #140 when recording the job").

**[B-2]** A-1 says `fleet_ci_targets` rebuild "keeps every row and reference unchanged" for seven inbound FKs, and Done-when extended requires a test asserting `pragma_foreign_key_list` of each of the seven referencing tables is unchanged after 0046. But the rebuild replays `fleet_ci_targets` and the migration also rebuilds `runners` — both inside the W-8 mechanism with `PRAGMA foreign_keys=OFF` and a temp-table guard. The guard catches dangling references before COMMIT, but nothing in the brief pins the rowids. SQLite FKs reference the logical PK, not rowid, so that part is fine. The problem is the "unchanged" assertion for `fleet_ci_targets` inbound FKs: `workload_placements`, `fleet_events`, etc. reference `fleet_ci_targets(id)` from 0022 with `ON DELETE no action` (W-5: "All of them are plain `REFERENCES fleet_ci_targets(id)` from 0022"). The rebuild is `CREATE TABLE x_new ...; INSERT INTO x_new SELECT ... FROM x; DROP TABLE x; ALTER TABLE x_new RENAME TO x`. Recreating the table drops and recreates the implicit index on the PK and any autoindexes — but more importantly, SQLite FKs are not stored as objects you can "recreate"; they are part of the table definition. If the new table's FK clauses are written the same, `pragma_foreign_key_list` of the *referencing* tables (which is what the test checks) will still point at `fleet_ci_targets` by name, and the referenced PK is the same. That is testable. The real hole: the test asserts "every row of every table is equal, with `fleet_ci_targets` rows gaining three NULL GitLab columns" — but rows are equal by content, not by rowid. Any FK from `host_target_grants` etc. references `fleet_ci_targets(id)`, a text PK, so content match is sufficient. This is not a block. Retract.

**[B-3]** A-1 says `fleet_ci_targets` gets "New columns, all nullable: `gitlab_connection_id TEXT REFERENCES gitlab_connections(id)`, `gitlab_project_id INTEGER`, `gitlab_group_id INTEGER`." Then the shape CHECK for `gitlab_project` requires `gitlab_connection_id` NOT NULL. But `gitlab_connection_id` is declared nullable, and the CHECK enforces NOT NULL only for that kind. That is coherent. However, the column-level `REFERENCES gitlab_connections(id)` FK has no `ON DELETE` action specified in A-1. The B-5/W-5 section pins actions for `runners.gitlab_connection_id` (`ON DELETE set null`) and `gitlab_jobs.connection_id` (`ON DELETE cascade`), but the `fleet_ci_targets.gitlab_connection_id` FK action is never stated. If left at SQLite default (`NO ACTION`), deleting a GitLab connection that has a fleet target would fail with an FK error, and nothing in #138 (DELETE connection, which returns 409 "while a pool targets it") covers a direct target reference without a pool. Is a `fleet_ci_targets` row without a pool possible? Yes — `ensure_target` creates it first, and pool-target sync comes later (#139). So #138's DELETE could hit an FK constraint it never anticipated. Fix: state the `ON DELETE` action for `fleet_ci_targets.gitlab_connection_id` explicitly (CASCADE to remove orphan targets? SET NULL is wrong because the shape CHECK requires non-NULL for GitLab kinds), and state what happens when a connection is deleted while a GitLab target still references it.

**[B-4]** The A-2 material type is "public" and pinned as a `#[derive(Clone, PartialEq, Eq, Serialize, Deserialize)]` struct with `deny_unknown_fields`. But the brief also says "a payload with another `kind` is rejected." With `#[serde(tag = "kind", rename = "gitlab_runner", deny_unknown_fields)]`, the `rename = "gitlab_runner"` is not a Rust attribute; serde's tag attribute uses `tag = "kind"` and the variant name or a `rename` on the *variant*. A struct is not a variant, so `rename = "gitlab_runner"` on a struct-level serde attribute is invalid or has no effect. The JSON `{"kind":"gitlab_runner",...}` would not deserialize into a struct tagged `kind` unless the struct has a field named `kind`. This is a concrete code-defect in the brief's own pinned type: the serde attribute as written cannot produce the serialized literal `{"kind":"gitlab_runner","token":"glrt-…","url":"https://gitlab.example.com"}`. Fix: either make `GitlabRunnerMaterial` an enum with a single variant `GitlabRunner { token, url }` and `#[serde(tag = "kind", rename_all = "snake_case")]`, or add an explicit `kind: &'static str` field (but then `deny_unknown_fields` plus an explicit `kind` field conflicts with tag-based serde). As written, B-4 blocks implementation of A-2.

**[B-5]** A-2 says `GitlabRunnerMaterial` derives `Debug` is "implemented by hand and prints `token: "[redacted]"`." But the struct has a `String` token, not `SecretString`. The brief's own evidence (the struct definition) shows `pub token: String`. A hand-written `Debug` that redacts a plain `String` field is possible, but then any `format!("{:?}", material)` in tests or logs will redact — fine. The contradiction is elsewhere: the issue text says the registration material is "the `glrt-` token" and the redaction section (NV-3) says the token prefix `glrt-` is added to `SECRET_PREFIXES`, which redacts by prefix *in strings*. A plain `String` token in `GitlabRunnerMaterial` that travels through `Debug` (hand-redacted) and through `AgentEvent` (prefix-redacted) is consistent. No block here. Retract.

**[B-6]** A-1 says `TargetKind` (`fleet/capabilities.rs`) gains `GitlabProject` and `GitlabGroup` "with wire `gitlab_project`, `gitlab_group`". But `CiTarget` is `#[serde(tag = "platform", rename_all = "snake_case")]` with variants `GitlabProject` and `GitlabGroup`, which serialize as `"platform":"gitlab_project"` and `"platform":"gitlab_group"` (Remaining scope notes). `TargetKind` is a *different* enum used in `SupportedRunner` (per A-1), but its serde wire format is not stated to be tagged. Does `TargetKind` use `#[serde(rename_all = "snake_case")]` internally (so `GitlabProject` -> `"gitlab_project"`)? The brief says "wire `gitlab_project`" — that is consistent with snake_case, but it must be explicit because `From<&CiTarget> for TargetKind` and `TargetKind::is_gitlab` feed the host-agent capability advertisement (#147, #142), which must match what the reconciler parses. If `TargetKind` already derives serde with its own tags or a different shape, the new variants' wire format must be pinned. Fix: state `TargetKind`'s serde attributes (or confirm `#[serde(rename_all = "snake_case")]` for untagged variant names), else #147 and #142 cannot implement `SupportedRunner` interoperably.

**[B-7]** The A-3 `GitLabCredentials` struct has `pub base_url: Url` and `pub access_token: SecretString`, and `FakeGitLab` keys state by `base_url` but the brief says "two connections on different instances stay apart." The phrase "different instances" is ambiguous — instances of what? If it means two different `Url` values (different GitLab hosts), that is covered by keying on `base_url`. If it means two `FakeGitLab` clones with different credentials but the same `base_url` (e.g. two access tokens for the same host), the state is keyed only by `base_url` and would *not* be isolated. The fake records `FakeCall { base_url, method }` and never the token, so two credentials on the same host are indistinguishable. Is that intended? The trait's design (A-3, per-call credentials) means there can be multiple tokens for one base_url. The fake's keying must be stated precisely: is it keyed by `(base_url, access_token)` or just `base_url`? If the latter, two connections on the same host with different tokens share state, and #138/#139 tests may get cross-contamination. Fix: state whether `FakeGitLab` distinguishes credentials or only base URLs, and what "two connections on different instances" means.

**[B-8]** W-4 pins `IdleExpired` and `RegistrationRefused` as `DiagnosticCode` variants. The issue text says "New outcome codes: `IdleExpired` ... and `RegistrationRefused`." The original scope listed them under "Agent protocol" with no owning enum. Clarifications NV-5 says "The outcome code enums are not in `agent.rs`; they are `FailureCode`, `UncertainCode` and `DiagnosticCode` in `crates/gridops-core/src/fleet/protocol/outcomes.rs`." W-4 pins them to `DiagnosticCode`. But the brief also says (Issue text, Agent protocol): "New outcome codes: `IdleExpired` (the runner waited its timeout without a job) and `RegistrationRefused`." and D5 in deviations says wire `idle_expired`, `registration_refused`. That is resolvable and W-4 is a clarification, not a contradiction. No block. Retract.

**[B-9]** The A-1 storage-glue item says `fleet::targets::ensure_target` "accepts the two GitLab variants and inserts the matching row. It still refuses Bitbucket with the existing error." But the issue text Scope says `CiTarget` gains two new variants, and the non-exhaustive site `admission.rs` target-row parser "ends in `_ => Err(FleetError::Invariant("invalid target kind"))`" — so `target_from_db` must be extended (stated). What is missing: what does `ensure_target` return, and what is the "existing error" for Bitbucket? The brief never names `ensure_target`'s signature or the existing Bitbucket refusal error. A round-trip test is specified ("`ensure_target` of a `CiTarget::GitlabProject`... then `target_from_db`... returns the same `CiTarget`"), but the return type and error variant for the refusal path are not pinned. Since #139 and #147 depend on `ensure_target` working, this blocks. Fix: state `ensure_target`'s return type (id? target? `Result<_, FleetError>`) and the exact error for the refused case.

**[B-10]** The A-1 `canonical_key` is "infallible, so the 'return an error' rule doesn't apply." But `canonical_key` is an existing exhaustive `match` over `CiTarget` (Clarifications NV-5). Adding `GitlabProject` and `GitlabGroup` arms to `canonical_key` that return a `String` is straightforward. The problem: `canonical_key` is `NOT NULL UNIQUE` on `fleet_ci_targets`, and the A-1 keys are `gitlab:project:{connection_id}:{project_id}`. But `project_id` is `ExternalId` = `NonZeroU64` at most i64::MAX, and `connection_id` is `GitlabConnectionId` (a newtype over `UpstreamText`, validated string). The canonical key format mixes a string (connection_id) with decimal integers. This is fine, but the A-1 shape CHECK requires `gitlab_project_id > 0` and the key is UNIQUE. No contradiction shown. Retract.

**[B-11]** W-8 migration mechanism says "Each rebuild = CREATE TABLE x_new (...); INSERT INTO x_new (<old columns>) SELECT <old columns> FROM x; DROP TABLE x; ALTER TABLE x_new RENAME TO x; then every index and trigger of x recreated." For `runners`, the B-5 list of indexes includes `runners_container_id_unique` UNIQUE (`container_id`), and the new columns are appended after `runtime`. The `DROP TABLE runners` inside `PRAGMA foreign_keys=OFF` with `runner_events.runner_id ON DELETE cascade` is harmless because FKs are off. But after `ALTER TABLE x_new RENAME TO x`, the inbound FKs from `runner_events`, `log_streams`, `workload_placements` still point at a table named `runners` — that is preserved. The guard `PRAGMA foreign_key_check` after the INSERTs but before COMMIT (with FKs off) will report violations only if dangling references exist from the old data. This is coherent. No block. Retract.

After retractions, the real blocks are B-1, B-3, B-4, B-6, B-7, B-9.

### WARN findings

**[W-1]** The A-2 `GitlabRunnerMaterial` uses `pub token: String` despite the issue text saying "the `glrt-` token" and the redaction mechanism operating on string prefixes. A `SecretString` would be more consistent with the `CreatedRunner` token type and would make the hand-written `Debug` redaction unnecessary. This is a design smell: a credential that must be hand-redacted in `Debug` and prefix-redacted in agent events is traveling as a plain `String`. Recommend `SecretString` here.

**[W-2]** A-1 adds `gitlab_connection_id TEXT REFERENCES gitlab_connections(id)` to `fleet_ci_targets` but does not state the ON DELETE behavior (B-3). Beyond the immediate FK action, the semantic is odd: a fleet target is an immutable identity, but a connection can be deleted (and its `gitlab_connections` row removed). If the FK is CASCADE, a target silently disappears and any `host_target_grants` referencing it become dangling (or the FK cascade would need to be on those inbound tables too). If NO ACTION, DELETE connection fails. Neither behavior is specified, and the "409 while a pool targets it" from #138 only covers the pool case.

**[W-3]** W-4 pins the two new codes to `DiagnosticCode` inside `CommandOutcome::Failed`, but the issue text simply says "New outcome codes." A reader of the final issue would need to know which enum gets them. Is there a reason `RegistrationRefused` is a Diagnostic and not a `FailureCode`? If #142 or #147 needs to branch on it to not retry, the `Failed { code: Configuration, diagnostic: Some(...) }` shape requires them to inspect `diagnostic` rather than the failure code itself. Clarify the decision rationale or make it a `FailureCode`.

**[W-4]** The A-3 `GitLabApi::job` and `pending_jobs` return `Job` with `tag_list: Vec<String>`, and `tag_list` is stored as JSON text in `gitlab_jobs`. Who does the serialization/deserialization? #146 implements the API and #140 stores jobs. If the JSON encoding of `tag_list` (e.g. an empty list as `"[]"`) is not pinned, #140 and #148 may diverge. The schema says `tag_list TEXT NOT NULL DEFAULT '[]'` but no serde format for the `Vec<String>` is specified.

**[W-5]** The A-1 shape CHECK for `gitlab_project` requires "every GitHub and Bitbucket column NULL" but does not enumerate which columns those are. A reader of the brief cannot verify the CHECK is complete without knowing the full `fleet_ci_targets` column list. This should be listed explicitly (e.g. `github_repository_id`, `github_organization_id`, `bitbucket_workspace_id`, `bitbucket_repository_id`).

**[W-6]** A-1 says the `fleet_ci_targets` rebuild adds "New columns, all nullable" but `gitlab_jobs.id` was added as a PK (B-1). There is no stated migration-order dependency: `gitlab_connections` is created first (W-5), so FKs from `fleet_ci_targets` and `runners` can reference it. But `fleet_ci_targets` rebuild (statement 5) depends on `gitlab_connections` existing (created statement 1), and `runners` rebuild (statement 6) depends on `gitlab_connections` (for FK) and possibly on `gitlab_jobs` (if FK from `runners.gitlab_connection_id` — no, that is to `gitlab_connections`). No explicit order problem. Fine.

**[W-7]** The W-8 guard checks `PRAGMA foreign_key_check` while FKs are OFF inside the transaction. SQLite's `foreign_key_check` is a no-op when FKs are off? The brief asserts it works as a guard. This needs verification against SQLite documentation: `PRAGMA foreign_key_check` "check[s] whether or not the database schema and the data in the database are consistent with respect to foreign keys" — it may work regardless of the `foreign_keys` setting because it is an explicit check, not an enforcement. This should be verified before implementation.

**[W-8]** The A-3 fake's `calls()` records `FakeCall { base_url, method }` and "The access token is never recorded." This is by design, but then `calls()` cannot distinguish two different credentials on the same `base_url` — the same ambiguity as B-7. If a test in #138 verifies that a call used token A vs token B, the recording cannot prove it. State whether credential identity is part of `FakeCall`.

### NIT findings

**[NIT-1]** The W-5 `gitlab_jobs` table has `status text NOT NULL` with a comment `-- JobStatus::as_str()`, but the `JobStatus` enum in A-3 has `#[serde(other)] Unknown`. If `Unknown` is deserialized from an unrecognized GitLab status, what string does `as_str()` return for `Unknown`? The open-jobs index `WHERE status NOT IN ('success','failed','canceled','skipped')` would treat `Unknown` as open, which may be wrong if the real status is terminal. This needs a defined mapping for `Unknown`.

**[NIT-2]** The D-deviation table says "Pool-target sync for GitLab is #139's" but the original issue text said "Syncing a pool's GitLab connections into fleet targets ... belongs to #139." Same thing. No issue.

**[NIT-3]** The A-2 test "a GitHub `PrepareEnvironment` fixture serializes byte for byte as it does on `master`" is good but the brief does not specify *where* this fixture lives or its exact JSON. A future implementer needs the fixture path and the expected bytes.

**[NIT-4]** The A-3 `JobStatus::is_terminal()` says "true exactly for Success | Failed | Canceled | Skipped." The issue text and W-5 say the open-jobs index uses `NOT IN ('success','failed','canceled','skipped')`. Consistent, but `Manual` and `Scheduled` are non-terminal and would be treated as open — is that correct for #148's polling? A scheduled job is not actionable. Clarify.
