## Brief Review (Round 1)

### BLOCK findings

**[B-1]** The `gitlab_jobs` schema does not include a `project_id` filter on the open-jobs index in W-5/W-6 — why it blocks — a group connection polls all projects in that group, and #140/#148 list jobs by project, so the reconciler's open-job scan cannot be filtered by the index as written; the index must be `WHERE status NOT IN ('success','failed','canceled','skipped') AND project_id IS NOT NULL` or the criterion must state that the open-jobs scan is per-project and accepts a full index scan.

**[B-2]** A-1 says the `gitlab_connection_id` FK on `fleet_ci_targets` has "no ON DELETE clause, so its action is SQLite's default, NO ACTION", but the same section says "#138's DELETE handler must check for a referencing fleet_ci_targets row and refuse with the same 409". These two statements are not contradictory in themselves, but the done-when criteria for the `fleet_ci_targets` rebuild do not include a test that a `DELETE FROM gitlab_connections` for a referenced connection actually fails with an FK error. Because the entire contract depends on that NO ACTION behavior to produce the API's 409, the missing test is a testability gap that must be fixed before implementation: add an acceptance criterion asserting the FK error occurs when a `fleet_ci_targets` row references the connection.

**[B-3]** The round-2 section R2-1 says the manager's `validate` gains a `("gitlab", _)` arm that returns `BadRequest("GitLab runners are not supported yet: Docker is #147, Tart is #142.")`. But the same section also says the Tart agent "gets the same arm, naming #142". The manager's arm names both #147 and #142, while the Tart agent's arm names only #142. That is fine, but the acceptance criteria do not specify which crate's error message is asserted in the tests. A test asserting the manager's message but not the Tart agent's, or vice versa, would pass while the other is wrong. This must be clarified: state exactly which error string each crate returns and that both are tested.

**[B-4]** The `GitLabRunnerMaterial` type in A-2 is `#[serde(tag = "kind", rename_all = "snake_case", deny_unknown_fields)]` with a single variant `GitlabRunner`. The brief claims this was checked against serde 1.0.229 and serde_json 1.0.151 in a scratch crate, and that it "serializes as the literal above" with `"kind":"gitlab_runner"`. But with `rename_all = "snake_case"` on an internally tagged enum, the tag value is derived from the variant name `GitlabRunner`, which snake_cases to `gitlab_runner`. That is consistent. However, the brief also claims the serialized JSON is exactly `{"kind":"gitlab_runner","token":"glrt-…","url":"https://gitlab.example.com","wait_timeout_seconds":600}`. The field order in serialized JSON is not guaranteed by serde for a derived `Serialize` and depends on the struct field order in the variant. The test that pins "the serialized string equals the literal above" is therefore not testable unless the implementation guarantees field order, which a derived `Serialize` does not. This must be fixed by either hand-implementing `Serialize` to guarantee order or changing the criterion to compare deserialization equivalence rather than byte-for-byte equality.

**[B-5]** The `FakeGitLab` recording section says `FakeCall { base_url: Url, method: FakeMethod }` records "every call, failed calls included, in order". The tests in `fake.rs` cover "the recorded calls", but the brief does not state that the tests assert the call order is exactly the order of invocation. Without an explicit assertion for ordering, the "in order" claim is untestable. Add an acceptance criterion that the `calls()` vector matches the invocation order, and that the test actually checks it.

**[B-6]** The W-4 section says `IdleExpired` and `RegistrationRefused` are added to `DiagnosticCode` in `fleet/protocol/outcomes.rs` with wire names `idle_expired` and `registration_refused`, and that there are serde round-trip tests for both codes inside a `CommandOutcome::Failed`. But the acceptance criteria in "Done when" only require "serde round-trip tests for the new variants" without specifying that they must be inside `CommandOutcome::Failed`. The brief's own evidence says the enums are `FailureCode`, `UncertainCode` and `DiagnosticCode` carried by `CommandOutcome`, and that a peer built before this change rejects a payload carrying the new codes. The done-when criterion must be made concrete: the round-trip tests must construct a `CommandOutcome::Failed` with each diagnostic code, serialize it, deserialize it, and assert the diagnostic code is preserved. Otherwise the test could be written against the enum alone and miss the integration with `CommandOutcome`.

**[B-7]** The D1 deviation moves the base URL from `ExecutionConfiguration` to `GitlabRunnerMaterial`, but the issue text also says "the registration material on stdin is the `glrt-` token, with the base URL in `configuration`". The A-2 section then says the test "pins that a GitHub `PrepareEnvironment` fixture serializes byte for byte as it does on `master`, which proves `ExecutionConfiguration` is untouched". But the issue text's original requirement that the GitLab base URL travels in `configuration` has been silently dropped in the deviation table. The brief says "Where it conflicts with anything above, this section wins", but D1 changes the issue text without an explicit acknowledgment in the acceptance criteria that the original requirement was replaced. This is a consistency issue: the done-when criteria must state that no `PrepareEnvironment` or `ExecutionConfiguration` field is added for the GitLab base URL, and that the base URL is exclusively in `GitlabRunnerMaterial`. If that is not stated, the implementation could add the field to `ExecutionConfiguration` and still pass all the listed tests.

**[B-8]** The `Scope::target` method in A-3 returns `CiTarget` and is called with `connection_id: GitlabConnectionId`, but the `CiTarget` variants are `GitlabProject { connection_id, project_id }` and `GitlabGroup { connection_id, group_id }`. The `Scope` enum has `Project { id: ExternalId, path: String }` and `Group { id: ExternalId, path: String }`, but the `target` method's implementation is described as `Project -> CiTarget::GitlabProject { project_id: id }, Group -> CiTarget::GitlabGroup { group_id: id }`. The `project_id` and `group_id` fields in `CiTarget` are `ExternalId`, so `id: ExternalId` maps correctly. However, the `connection_id` is passed as an argument, not part of `Scope`. This is fine, but the brief does not state what type `connection_id` is in the `Scope::target` signature beyond `GitlabConnectionId`. That is specified. No block.

### WARN findings

**[W-1]** The `gitlab_jobs` table has no `project_path` or `project_name` column, even though `resolve_scope` returns `Scope::Project { path: String }`. The reconciler and API may need to display or filter by project path, which would require a join or an additional column. If the contract intends to store only the numeric `project_id`, that is fine, but the brief does not state whether `project_id` alone is sufficient for all wave-1 consumers. Recommendation: confirm that no wave-1 issue needs the project path in `gitlab_jobs`.

**[W-2]** The `FakeGitLab` keys state by `base_url` alone and never inspects the token, which means two tokens on the same base URL share state. The brief says tests needing isolation must give different base URLs. This is a reasonable simplification, but it means the fake cannot test scenarios where two connections on the same GitLab server have different permissions. If #138 or #140 needs to test permission isolation, the fake must be extended. Recommendation: note this limitation explicitly in the fake's doc comment.

**[W-3]** The `GitlabRunnerMaterial` type has `token: String` rather than `SecretString`. The brief justifies this in the carried findings B-5 by saying the existing host-agent `Material` types also carry tokens as `String`. This is consistent, but the type is public in `gridops-core` and could be logged accidentally by code that doesn't know to redact it. Recommendation: add a doc comment on the `token` field stating it is secret and must never be logged, or use a newtype with a redacting `Debug`.

**[W-4]** The `ProvisionRunner` structs in `gridops-manager` and `gridops-tart-agent` gain `gitlab_runner_token: Option<String>` with wire name `gitlabRunnerToken`. The brief says it is a secret and is never logged, but it is a plain `String` in the struct. Recommendation: use a `SecretString` or a newtype with a redacting `Debug` in the future, and ensure the current code's logging paths are audited in #147 and #142.

**[W-5]** The `fleet_ci_targets` rebuild in A-1 adds three nullable GitLab columns, but the per-kind shape CHECK requires that for GitHub and Bitbucket kinds, all three GitLab columns are NULL. This means the CHECK expression grows by three terms per arm, which is verbose but correct. Recommendation: consider using a helper view or generated column if the expression becomes unreadable, but do not change the contract without a new review.

**[W-6]** The `runner_pool_gitlab_connections` table is specified to exactly mirror `runner_pool_bitbucket_connections` including its indexes, but the index `runner_pool_gitlab_connections_connection_idx` is described as `(connection_id, pool_id)` without a WHERE clause. The Bitbucket index is also a full index. This is fine, but if the table is large, a partial index on active pools may be useful. Recommendation: leave as specified for wave 0.

**[W-7]** The OpenAPI section W-7 says the `DELETE /api/v1/platform-connections/gitlab/{connection_id}` 409 covers "a GitLab `fleet_ci_targets` row that still references the connection", and A-1 says the FK is NO ACTION so the delete would fail. The API spec does not include a `409` response for `DELETE` in the listed responses, only `204` and `409`. That is consistent. Recommendation: ensure the `GridlabConnection` schema in the spec does not include a `webhookUrl` or `webhookSecret`, as those are only in the create and rotate responses.

### NIT findings

**[NIT-1]** The `JobStatus` enum includes `Created`, `WaitingForResource`, `Preparing`, `Pending`, `Running`, `Success`, `Failed`, `Canceled`, `Skipped`, `Manual`, `Scheduled`, and `Unknown`. The open-jobs index treats `Manual` and `Scheduled` as open, but the brief notes "Whether #148 acts on an open `Manual` or `Scheduled` job is #148's behaviour, not part of this contract." This is fine, but the index may grow large if many manual or scheduled jobs are recorded. Recommendation: consider whether a separate status filter is needed for the reconciler's poll.

**[NIT-2]** The `gitlab_jobs.tag_list` default is `'[]'` and the encoding is compact JSON via `serde_json::to_string`. This is fine, but if the API returns tags in a different order than the job's creation, the unique index on `(connection_id, job_id)` does not conflict, so no issue.

**[NIT-3]** The `FakeGitLab` `runners(base_url)` method returns `FakeRunner { id, scope, tags, run_untagged, description }` but not the token. The brief says the fake never records the token. This is fine for tests that need to verify runner creation, but a test that needs to assert the token format must use the `create_runner` return value.

**[NIT-4]** The `GitLabCredentials` struct has `pub base_url: Url` and `pub access_token: SecretString`, and `Debug` prints `base_url` and `"[redacted]"`. The `SecretString` type already redacts its `Debug`, so the manual `Debug` for the token is redundant unless the brief means the entire struct's `Debug` output excludes the token's debug entirely. This is a minor clarity issue.

**[NIT-5]** The `Scope::target` method is described as `Scope::target(connection_id: GitlabConnectionId) -> CiTarget`, but the `Scope` enum has no `connection_id` field. The method takes `connection_id` as an argument, which is fine, but the signature as written could be misread as a method on `Scope` that returns a target with the given connection id. No change needed.

### Verdict

BLOCK — 8 blocking findings; must resolve before implementation starts.
