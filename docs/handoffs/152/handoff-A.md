## Summary
BLOCK, with 1 block and 4 warn findings.

- **The block: the batched DELETE the brief specifies does not bound its scan.** Each pass ends with a batch that finds fewer than 500 eligible rows, and in steady state that is every pass. That batch reads the whole retained table while it holds SQLite's write lock.
  - **The cause:** `received_at` has no index, so the inner `ORDER BY snap.rowid LIMIT ?` can stop early only when it fills the batch.
  - **The precedent it repeats:** `migrations/0034_retention_indexes.sql` was written to fix this same defect on `webhook_deliveries`.
  - **The brief's check would pass it:** its `EXPLAIN QUERY PLAN` acceptance test accepts this plan.
- **Everything else matches the codebase's patterns.** The retention rule, the reader inventory, the settings contract, the autocommit batches and the warn-and-continue wiring all match their neighbours.

**Checked and consistent (no finding):**
- **The reader inventory is accurate.**
  - The only non-test readers are the five the brief lists: `inventory.rs:97-104` (the resend), `registry/mod.rs:1287-1312`, and `queries.rs:1134`, `:1354` and `:1912`. Each reads only the session's current sequence, and each requires `s.ended_at IS NULL`.
  - The resend path cannot reach an ended session, because `load_current_session` filters `ended_at IS NULL` (`inventory.rs:409`). So the brief's rule to prune the current snapshot of an ended session is safe.
  - `current_inventory_sequence` only increases (`inventory.rs:87`), so a row that is no longer current never becomes current again.
  - Ignoring `receipt_state` is correct.
- **The schema allows the delete.** No FK references `fleet_inventory_snapshots`, and it has no DELETE trigger. Its own FK points at the parent `fleet_observation_sessions`, so deleting child rows needs no parent check. The `NOT EXISTS` uses the `(host_id,session_id)` autoindex on the real schema, so no sessions index is needed.
- **The batches are autocommit statements on `&app.database`.** That matches every other delete in `cleanup_retention` (`main.rs:3290-3349`).
- **The wiring follows `reconcile()`'s pattern.** Warn-and-continue with `if let Err(error) = … { tracing::warn!(…) }` is the pattern `reconcile()` uses for each step (`main.rs:604-613`). `cleanup_retention` also runs on the manager-unavailable path (`:638`), so the prune runs there too.

  - The optional `#[serde(default)] Option<i64>` field follows `macos_vm_slots` (`resources.rs:268-270`), so the existing web client (`src/routes/settings.general.tsx`), which does not send it, keeps working.
  - The range `1..=3_650` matches the other retention days (`resources.rs:3593-3596`).
  - Clamping at use follows `enforce_log_storage_budget`'s `.clamp` (`main.rs:3355-3357`).
