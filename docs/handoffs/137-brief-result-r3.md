## Brief Review (Round 1)

### BLOCK findings

### Resolved findings

**[R-1]** **[B-1]** The `gitlab_jobs` schema is internally inconsistent. The W-5/W-6 pinned table defines `id` as `text PRIMARY KEY NOT NULL`, but the original issue scope says `gitlab_jobs` has a "unique index on `(connection_id, job_id)`". A PRIMARY KEY on `id` plus a UNIQUE index on `(connection_id, job_id)` is coherent, but no column named `id` appears anywhere else in the brief (the `Job` struct in A-3 has no `id` field, and `tag_list` is the only JSON column). What is the semantic of `gitlab_jobs.id`? Is it a UUID? A composite of connection and job? This must be specified or no implementer can write the INSERT in #140 or the SELECT in #148. Fix: specify the type and source of `id` (e.g. "UUID generated by #140 when recording the job").

**[R-2]** **[B-3]** A-1 says `fleet_ci_targets` gets "New columns, all nullable: `gitlab_connection_id TEXT REFERENCES gitlab_connections(id)`, `gitlab_project_id INTEGER`, `gitlab_group_id INTEGER`." Then the shape CHECK for `gitlab_project` requires `gitlab_connection_id` NOT NULL. But `gitlab_connection_id` is declared nullable, and the CHECK enforces NOT NULL only for that kind. That is coherent. However, the column-level `REFERENCES gitlab_connections(id)` FK has no `ON DELETE` action specified in A-1. The B-5/W-5 section pins actions for `runners.gitlab_connection_id` (`ON DELETE set null`) and `gitlab_jobs.connection_id` (`ON DELETE cascade`), but the `fleet_ci_targets.gitlab_connection_id` FK action is never stated. If left at SQLite default (`NO ACTION`), deleting a GitLab connection that has a fleet target would fail with an FK error, and nothing in #138 (DELETE connection, which returns 409 "while a pool targets it") covers a direct target reference without a pool. Is a `fleet_ci_targets` row without a pool possible? Yes — `ensure_target` creates it first, and pool-target sync comes later (#139). So #138's DELETE could hit an FK constraint it never anticipated. Fix: state the `ON DELETE` action for `fleet_ci_targets.gitlab_connection_id` explicitly (CASCADE to remove orphan targets? SET NULL is wrong because the shape CHECK requires non-NULL for GitLab kinds), and state what happens when a connection is deleted while a GitLab target still references it.

**[R-3]** **[B-4]** The A-2 material type is "public" and pinned as a `#[derive(Clone, PartialEq, Eq, Serialize, Deserialize)]` struct with `deny_unknown_fields`. But the brief also says "a payload with another `kind` is rejected." With `#[serde(tag = "kind", rename = "gitlab_runner", deny_unknown_fields)]`, the `rename = "gitlab_runner"` is not a Rust attribute; serde's tag attribute uses `tag = "kind"` and the variant name or a `rename` on the *variant*. A struct is not a variant, so `rename = "gitlab_runner"` on a struct-level serde attribute is invalid or has no effect. The JSON `{"kind":"gitlab_runner",...}` would not deserialize into a struct tagged `kind` unless the struct has a field named `kind`. This is a concrete code-defect in the brief's own pinned type: the serde attribute as written cannot produce the serialized literal `{"kind":"gitlab_runner","token":"glrt-…","url":"https://gitlab.example.com"}`. Fix: either make `GitlabRunnerMaterial` an enum with a single variant `GitlabRunner { token, url }` and `#[serde(tag = "kind", rename_all = "snake_case")]`, or add an explicit `kind: &'static str` field (but then `deny_unknown_fields` plus an explicit `kind` field conflicts with tag-based serde). As written, B-4 blocks implementation of A-2.

**[R-4]** **[B-6]** A-1 says `TargetKind` (`fleet/capabilities.rs`) gains `GitlabProject` and `GitlabGroup` "with wire `gitlab_project`, `gitlab_group`". But `CiTarget` is `#[serde(tag = "platform", rename_all = "snake_case")]` with variants `GitlabProject` and `GitlabGroup`, which serialize as `"platform":"gitlab_project"` and `"platform":"gitlab_group"` (Remaining scope notes). `TargetKind` is a *different* enum used in `SupportedRunner` (per A-1), but its serde wire format is not stated to be tagged. Does `TargetKind` use `#[serde(rename_all = "snake_case")]` internally (so `GitlabProject` -> `"gitlab_project"`)? The brief says "wire `gitlab_project`" — that is consistent with snake_case, but it must be explicit because `From<&CiTarget> for TargetKind` and `TargetKind::is_gitlab` feed the host-agent capability advertisement (#147, #142), which must match what the reconciler parses. If `TargetKind` already derives serde with its own tags or a different shape, the new variants' wire format must be pinned. Fix: state `TargetKind`'s serde attributes (or confirm `#[serde(rename_all = "snake_case")]` for untagged variant names), else #147 and #142 cannot implement `SupportedRunner` interoperably.

**[R-5]** **[B-7]** The A-3 `GitLabCredentials` struct has `pub base_url: Url` and `pub access_token: SecretString`, and `FakeGitLab` keys state by `base_url` but the brief says "two connections on different instances stay apart." The phrase "different instances" is ambiguous — instances of what? If it means two different `Url` values (different GitLab hosts), that is covered by keying on `base_url`. If it means two `FakeGitLab` clones with different credentials but the same `base_url` (e.g. two access tokens for the same host), the state is keyed only by `base_url` and would *not* be isolated. The fake records `FakeCall { base_url, method }` and never the token, so two credentials on the same host are indistinguishable. Is that intended? The trait's design (A-3, per-call credentials) means there can be multiple tokens for one base_url. The fake's keying must be stated precisely: is it keyed by `(base_url, access_token)` or just `base_url`? If the latter, two connections on the same host with different tokens share state, and #138/#139 tests may get cross-contamination. Fix: state whether `FakeGitLab` distinguishes credentials or only base URLs, and what "two connections on different instances" means.

**[R-6]** **[B-9]** The A-1 storage-glue item says `fleet::targets::ensure_target` "accepts the two GitLab variants and inserts the matching row. It still refuses Bitbucket with the existing error." But the issue text Scope says `CiTarget` gains two new variants, and the non-exhaustive site `admission.rs` target-row parser "ends in `_ => Err(FleetError::Invariant("invalid target kind"))`" — so `target_from_db` must be extended (stated). What is missing: what does `ensure_target` return, and what is the "existing error" for Bitbucket? The brief never names `ensure_target`'s signature or the existing Bitbucket refusal error. A round-trip test is specified ("`ensure_target` of a `CiTarget::GitlabProject`... then `target_from_db`... returns the same `CiTarget`"), but the return type and error variant for the refusal path are not pinned. Since #139 and #147 depend on `ensure_target` working, this blocks. Fix: state `ensure_target`'s return type (id? target? `Result<_, FleetError>`) and the exact error for the refused case.

### WARN findings

**[W-1]** The `GitlabRunnerMaterial` uses `pub token: String` with a hand-written redacting `Debug` and prefix-based redaction in `session.rs`. This is internally consistent and the brief explicitly tests that `format!("{:?}")` does not contain the token. However, the token is a credential traveling as a plain `String` through the sealed bootstrap material. Any code path that logs the material before it reaches `Debug` (e.g. `eprintln!("{:?}", material)` is covered, but a future `derive(Display)` or `serde_json::to_string` in a debug log would not be) could leak it. Recommend documenting that the token must never be serialized or logged except through the pinned `Debug` and `redact` paths, or consider a wrapper type with a `Serialize` impl that redacts by default.

**[W-2]** The W-8 migration mechanism pins `PRAGMA foreign_keys=OFF` outside the transaction, then `PRAGMA foreign_key_check` via a temp-table guard inside the transaction. The brief's evidence section states this was checked against SQLite 3.54.0 with one dangling child row. This is adequate for the contract, but the migration is unprecedented in this codebase (no migration in `migrations/` has rebuilt a table before). A failure mid-migration leaves `foreign_keys` OFF on the pooled connection if the migration panics or errors before the final `PRAGMA foreign_keys=ON`. Recommend a test that simulates a guard failure and asserts the connection is still usable with `foreign_keys` ON afterwards (or documents that the migrator handles this).

**[W-3]** The `fleet_ci_targets` rebuild adds a `gitlab_connection_id` FK with SQLite default NO ACTION, and the DELETE connection 409 in W-7 covers the fleet-target reference case. This is coherent, but it means a GitLab connection can never be deleted while any fleet target references it, and there is no way to delete a fleet target in this contract. A user who creates a GitLab target (via #139's pool-target sync) and then removes the pool is left with a permanent fleet target that blocks connection deletion. The brief notes this is the same as Bitbucket today, but for Bitbucket the fleet-target path is newer and may not have hit this case in production. Recommend documenting the cleanup story for orphaned GitLab fleet targets (e.g. a future #139 or #138 needs a target-deletion path) or adjusting the FK to CASCADE with compensating inbound FK changes.

**[W-4]** The A-1 shape CHECK for `gitlab_project` and `gitlab_group` requires "every GitHub and Bitbucket column NULL" and enumerates them as `installation_id`, `repository_id`, `organization_id`, `bitbucket_connection_id`, `workspace_uuid`, `repository_uuid`. The W-5 table for `fleet_ci_targets` rebuild says the new GitLab columns come "after `repository_uuid`, in that order." This is precise. However, the Done-when extension says the shape CHECK "refuses a GitLab row with a GitHub column set" — but which GitHub column? The test must set one of the six to a non-NULL value and assert refusal. The brief does not pin which column the test exercises. Recommend specifying at least one concrete refused case (e.g. `gitlab_project` row with `installation_id = 123`) so the test is deterministic.

**[W-5]** The `JobStatus` enum has `#[serde(other)] Unknown` and `is_terminal()` returns false for it, so `Unknown` jobs stay in the open-jobs index and remain "unconcluded" forever. The brief's NIT-4 from the earlier round notes this and defers the filtering decision to #148. This is acceptable for a contract, but if the GitLab API introduces a new terminal status after this contract ships, the reconciler will poll those jobs indefinitely until the enum is updated. Recommend #148 implement a conservative timeout or an explicit filter for `Unknown` jobs, or the `JobStatus` enum be made non-exhaustive so future statuses cause a compile error rather than silent `Unknown`.

### NIT findings

**[NIT-1]** The W-5 table for `gitlab_jobs` uses `tag_list text NOT NULL DEFAULT '[]'` with a comment `-- JSON array of strings`. The encoding is pinned elsewhere as `serde_json::to_string(&job.tag_list)` of the `Vec<String>`. This is adequate, but the column default `'[]'` is only correct if the empty `Vec<String>` serializes as `[]`, which it does. No action needed, but an implementer might mistake the default for a `json` column type. Recommend adding a comment that the column is TEXT-encoded JSON, not SQLite's JSON type.

**[NIT-2]** The `Scope` enum in A-3 has `Scope::target(connection_id: GitlabConnectionId) -> CiTarget`, but the W-5 `gitlab_connections` table stores `scope_id` as `integer` and `scope_path` as `text`. The `Scope::Project { id: ExternalId, path: String }` uses `ExternalId` for `id`, which is a `NonZeroU64` at most `i64::MAX`. The table's `scope_id INTEGER NOT NULL CHECK (scope_id > 0)` is consistent with this. No action needed, but the wire format (JSON) for `Scope` is not pinned — will it serialize as `{"kind":"project","id":123,"path":"group/sub/project"}` or something else? Since `Scope` is not a wire type in the API spec (the connection CRUD uses `scopeKind` and `scopePath` separately), this is only important for tests. Recommend pinning it in a serde test if it will ever cross a serialization boundary.

**[NIT-3]** The A-2 test "a GitHub `PrepareEnvironment` fixture serializes byte for byte as it does on `master`" pins the expected bytes as a string literal "captured on `master` before any change in this issue. The literal is checked in as captured and is not edited by hand." This is a good regression test, but the brief does not specify which Rust version or serde version produces those bytes. Since the test is in the same workspace with locked dependencies, this is safe. No action needed.

**[NIT-4]** The W-8 guard uses `CREATE TEMP TABLE _gitlab_0046_fk_guard (violations INTEGER NOT NULL CHECK (violations = 0));` followed by `INSERT INTO _gitlab_0046_fk_guard SELECT count(*) FROM pragma_foreign_key_check;`. If `pragma_foreign_key_check` returns zero rows (no violations), `count(*)` is 0 and the INSERT succeeds. If it returns one row per violation, the count is the number of violations and the CHECK fails. This is correct. However, the temp table name `_gitlab_0046_fk_guard` is hardcoded and could collide with a future migration's temp table of the same name if two migrations run in the same session. Since migrations are sequential and temp tables are connection-scoped, this is unlikely but worth noting.

**[NIT-5]** The D-deviation table row D6 says "adds `ensure_target`/`target_from_db` arms. Pool-target sync for GitLab is #139's." This is clear, but the original issue text's Done-when does not mention testing the GitLab `ensure_target` round trip in the Done-when section — it is only in the "Done-when, extended for A-1" amendment. An implementer reading only the original Done-when might miss the round-trip test. Recommend updating the original Done-when or adding a cross-reference in the issue text.

### Verdict

PASS — no BLOCK findings; implementation may proceed.
