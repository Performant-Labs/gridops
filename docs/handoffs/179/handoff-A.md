## Summary
BLOCK, with 2 block and 6 warn findings. Part 1 extends the right objects at the right layer: it rewrites the two in-lock statements so they reach the existing `host_commands_poll_idx`, and it keeps the read-only pre-check. Two parts of the plan would build the wrong thing:
- **Part 2 is a no-op.** `log_slow_statements(Warn, 1 s)` is already sqlx 0.9's default. The `sqlx::query` events it controls are also dropped by the api's and the reconciler's default log filters. The done-when would pass on a change that adds no visibility.
- **Part 3 retries a 503 on the command poll inside the session.** The poll has no replay rule. The repo's settled recovery for a poll reply lost after the API delivered a command is: end the session, then let the handshake's `settle_unreceived` settle it. A green test pins that recovery. Retrying the poll in-session brings back the 2026-10-14 21:05 lockout, and the brief's own done-when requires it.
