## Brief Review (Round 1)

### BLOCK findings

**[B-1]** [new, completeness] The acceptance criterion for payload equality requires Vitest `toEqual` comparison of `data` objects where "keys set to `undefined` count as absent (as `JSON.stringify` drops it)." The brief correctly notes that `toEqual` treats `{ repositoryIds: undefined }` as equal to `{}`. However, the acceptance criterion for the payload-equality cases states: "The expected objects are the frozen old-form constants described in 'Payload-equality reference (frozen old-form output)' below." The brief's "Payload-equality reference" section specifies T captures these constants by rendering the old forms at commit `5550cf5`. The "Sequencing gate" section then lays out a detailed procedure (steps 1-5) for capturing from a pre-change tree. This resolves the circular dependency identified in earlier rounds. However, the acceptance criterion itself ("Vitest payload-equality cases… The expected objects are the frozen old-form constants described in 'Payload-equality reference (frozen old-form output)' below, not values computed by the new code") does not actually require the comparison to use `toEqual` with the `undefined`-as-absent semantics. The "Payload-equality reference" section says "Comparison is Vitest `toEqual` on the `data` object (keys set to `undefined` count as absent, as Required design 3 states)." But the acceptance criterion text does not mention `toEqual`, nor does it state the `undefined`-as-absent rule. An implementer reading only the acceptance criteria could reasonably substitute `toStrictEqual` (which treats `{ repositoryIds: undefined }` and `{}` as different) and fail the test incorrectly. — Must add to the payload-equality acceptance criterion: "Comparison is Vitest `toEqual` (not `toStrictEqual`), because `JSON.stringify` drops keys set to `undefined`; a key set to `undefined` counts as absent."

**[B-2]** [new, completeness] The acceptance criterion for the mixing-rules test requires "(e) selecting a GitHub repository, then a Bitbucket workspace, then removing the repository leaves the workspace selected, and submitting sends no `POST /api/v1/runner-pools` (the stubbed `fetch` records none) and shows the parse error in the 'Could not create the pool' callout, as the Target-kind contract's `requires`/`standalone` entry states." The Target-kind contract explains this behavior: the picker does not block deselection, the submit button stays enabled (line 494 disables it only on `submitting || options.installations.length === 0`), and `parseCreateRunnerPoolInput` rejects the payload (`installationId: 0` fails `positive()`). However, the brief does not show `runner-pools.new.tsx` lines 489 or 494 in the SOURCE EXCERPTS. The brief's "Source material read" section says these were added in the round-2 amendment pass ("plus grep for the submit button and error callout, lines 489 and 494"), but the excerpt is not present. The claim that the submit button stays enabled in this state and that the error callout displays the thrown message is a specific behavioral claim about code not shown. If line 494 actually disables the submit button under some other condition, or if the error callout does not display thrown errors from `createRunnerPoolAction`, the test would fail. — Must show `runner-pools.new.tsx` lines 489 and 494 (submit button disabled condition and error callout rendering) in the SOURCE EXCERPTS.

**[B-3]** [new, completeness] The acceptance criterion for partial load failure states: "when one platform's list binding rejects and the other resolves, the page still renders the resolved platform's connections, shows a per-platform error with a Retry control for the failed one, and Retry re-runs only that load." The brief's "Connections page loading" section specifies `Promise.allSettled` per platform and "mutations call `router.invalidate()`" for retry. However, the brief does not specify how Retry re-runs only the failed platform's load. `router.invalidate()` typically invalidates the route loader, which would re-run `Promise.allSettled` over all platforms, not just the failed one. The acceptance criterion requires "Retry re-runs only that load," but no mechanism is specified to achieve this (e.g., per-platform query with manual refetch, or a state flag that excludes successful platforms from re-run). Without a specified mechanism, the test cannot be written, and the implementation may not satisfy the criterion. — Must specify how Retry re-runs only the failed platform's load (e.g., a per-platform query with `refetch()`, or a `retryPlatform(id)` function that updates a `pendingRetries` set consumed by the loader).

**[B-4]** [new, completeness] The acceptance criterion for permission gating states: "Vitest (or the Playwright walkthrough) covers the Connections page's permission gating — Add, Edit and Remove are hidden when the descriptor reports the user cannot manage, shown when it can — and the post-create one-time reveal dialog, driven by a test-only descriptor whose post-create hook returns a value: the value is shown once after create and not again after the dialog closes." The brief specifies that the page component "takes the descriptor list as a prop (default: the production `platforms`) so tests can inject a test-only descriptor with a post-create hook without adding it to production." However, the descriptor's `canManage` is described as a binding ("whether the current user can manage; each binding is optional per descriptor"). The GitHub descriptor's `canManage` comes from `user.role` and each installation's `permission` (lines 30, 76, 95-97 of `settings.github.tsx`). The acceptance criterion tests that "Add, Edit and Remove are hidden when the descriptor reports the user cannot manage." But the GitHub descriptor has no create/update/remove connection functions (installations are managed externally), so "Add, Edit and Remove" for GitHub connections are not applicable. The criterion must specify which platform's connections are being tested for permission gating. If it is Bitbucket, the descriptor's `canManage` is `getBitbucketConnections().canManage` (a single boolean). If it is a test-only descriptor, the test must inject one with a `canManage` field, but the criterion does not state this. — Must clarify which descriptor(s) the permission-gating test uses and what `canManage` values are exercised (e.g., Bitbucket descriptor with `canManage: true` and `canManage: false`, or a test-only descriptor with an injectable `canManage` flag).

### WARN findings

**[W-1]** The acceptance criterion for redirects states: "Verified by a Vitest assertion on the rendered `href`/redirect target, plus a grep over `src/` showing no remaining `"/settings/github"` or `"/settings/integrations"` string outside the two redirect-only route files." The brief's grep excludes `routeTree.gen.ts` and `/api/v1/` paths, but the acceptance criterion text does not state these exclusions. An implementer running the grep without exclusions would find false positives in `routeTree.gen.ts` (generated route constants) and possibly in API path strings. Recommend updating the acceptance criterion to include the exclusions: "grep over `src/` (excluding `routeTree.gen.ts` and `/api/v1/` paths) showing no remaining…"

**[W-2]** The brief's "Connections page loading" section states "GitHub data reuses the `/settings` loader data (`getSettingsPage()`), not a second fetch." However, the GitHub descriptor's list binding reads `page.data.installations` (from the parent loader), while the Bitbucket descriptor's list binding reads `getBitbucketConnections()` (a separate fetch). The acceptance criterion for partial load failure assumes one platform's list binding can reject. If the GitHub descriptor's list binding does not actually fetch (it reads already-loaded data from the parent), then the partial load failure test would only exercise the Bitbucket fetch failing. The criterion says "when one platform's list binding rejects and the other resolves," implying both platforms have fetch-based list bindings. This is inconsistent with the GitHub descriptor reading from the parent loader. Recommend clarifying whether the partial load failure test uses two test-only descriptors with fetch-based list bindings (to exercise the failure path generically) or one production descriptor plus one test-only descriptor.

**[W-3]** The acceptance criterion for the mixing-rules test requires "(a) with no GitHub target selected, every Bitbucket workspace option is disabled and shows a reason (Bitbucket is not standalone), and becomes selectable once a GitHub repository or runner group is selected." The Target-kind contract specifies `requires`/`standalone` as a per-kind field, with Bitbucket workspace requiring a GitHub target. However, the contract does not specify how the picker determines "a GitHub target" when the requirement is between platforms (GitHub) rather than specific kinds. The contract defines `requires`/`standalone` only as a boolean ("Bitbucket workspace is not standalone — it requires a GitHub target"), but does not define the value of `requires` (is it `"github.repository"`, `"github.runner-group"`, or a platform-level requirement?). The implementation needs a precise `requires` value to compute disabled states. Recommend specifying the exact `requires` value for the Bitbucket workspace kind (e.g., `requires: { anyOf: ["github.repository", "github.runner-group"] }` or a platform-level requirement).

**[W-4]** The brief's "Verified source excerpts" section states: "`settings.github.tsx` route and data source (`src/routes/settings.github.tsx` lines 17 and 20-30; settles NV-3). The route declares only `component` (no `loader`, no `beforeLoad`, no action export)." However, the excerpt shown includes line 20: `export const Route = createFileRoute("/settings/github")({ component: GitHubSettings });` with no `beforeLoad`. The "GitHub App section wiring" section then specifies the redirect-only `/settings/github` route uses `beforeLoad: () => { throw redirect({ replace: true, to: "/settings/connections" }) }` with no loader and no component. The acceptance criterion requires `/settings/github` to redirect. This is consistent, but the brief does not state whether the redirect test renders the redirect-only route in isolation or navigates to it. Recommend specifying how the redirect is tested (e.g., a Vitest assertion that the route's `beforeLoad` throws a redirect with `to="/settings/connections"` and `replace: true`).
