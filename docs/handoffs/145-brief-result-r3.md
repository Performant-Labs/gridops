## Brief Review (Round 1)

### BLOCK findings

**[B-1]** [new, completeness] The acceptance criterion for the `?appError=` handling specifies a Vitest assertion that calls `beforeLoad` with `preload: true` and expects "it throws the same redirect without toasting". The brief does not state how `preload` is passed to `beforeLoad` in the test harness, nor what "without toasting" is asserted against (e.g., a mocked `toast` module's call count). The shown `settings.index.tsx` excerpt (lines 4–14) does show `if (!preload) toast.error(search.appError)`, so the behavior is derivable from source. However, the acceptance criterion is written as a test instruction ("Vitest asserts...") without specifying the mocking strategy for `toast` or how `beforeLoad` is invoked. A test author could write a passing test that mocks `toast` incorrectly (e.g., asserting `toast.error` is not called when it is, but the mock is set up to swallow calls) and still satisfy the literal criterion. The brief must specify the test harness: how `beforeLoad` is called (direct invocation with a fabricated `{ location, preload }` object, or through the route's `beforeLoad` export), how `toast.error` is spied/mocked, and what "without toasting" asserts (e.g., `expect(toast.error).not.toHaveBeenCalled()`).

**[B-2]** [new, correctness] The acceptance criterion for the grep check says "The 'two redirect-only route files' are exactly `src/routes/settings.github.tsx` and `src/routes/settings.integrations.tsx`, whose only permitted hits are their own `createFileRoute("/settings/github")` / `createFileRoute("/settings/integrations")` declarations (today lines 20 and 21)". The shown `settings.integrations.tsx` excerpt in the Source material read list states the route declaration is at line 21 (`createFileRoute("/settings/integrations")`), which is consistent. However, the brief earlier states under "Codebase starting points" that `settings.integrations.tsx` line 21 is `createFileRoute("/settings/integrations")` and line 23 is `component: BitbucketSettings`. This is an assertion about the file's contents, not a shown excerpt in this prompt (the SOURCE EXCERPTS section does not include `settings.integrations.tsx`). The grep criterion depends on the exact line numbers of the route declarations, but those line numbers are asserted in prose, not shown. If the file has drifted (e.g., a comment added above the declaration), the "only permitted hits" boundary could shift. This is a testability issue: the criterion references line numbers that are not pinned by a shown excerpt, so a reviewer cannot verify the boundary is enforceable. The brief must either quote the relevant lines of both redirect-only route files in the SOURCE EXCERPTS, or define the exclusion by pattern (e.g., "lines matching `createFileRoute("/settings/github")`") rather than by line number.

**[B-3]** [new, completeness] The acceptance criterion for "no platform-specific rows outside Targets and Platform options" prohibits "no expression compares against a platform id or kind id (`"github"`, `"bitbucket"`, `"github.repository"`, …), tests `pool.scope`, or tests a platform-named field (`bitbucketConnectionIds.length`, `scope === …`) to choose what a shared row renders". The "Other sites now in scope" section says `ReadOnlyPool` in `runner-pools.$poolId.settings.tsx` "branches on `pool.scope` → render its targets through the same registry-driven target display (read-only)". The acceptance criterion's precise wording ("no expression... tests `pool.scope`") would prohibit the `ReadOnlyPool` change from using `pool.scope` at all, yet the required change is to render targets differently based on `pool.scope`. This is a direct contradiction between the acceptance criterion's blanket prohibition and the specific requirement to branch on `pool.scope` in `ReadOnlyPool`. The brief must reconcile these: either `ReadOnlyPool`'s `pool.scope` branching is explicitly exempted (e.g., "except for `ReadOnlyPool`'s target display, which must derive target kinds from `pool.scope` via `targets.ts`"), or the criterion must define "shared rows" to exclude `ReadOnlyPool`.

### WARN findings

**[W-1]** The acceptance criterion for the grep check prohibits any match of `settings/github` or `settings/integrations` in `src/` outside the two redirect-only route declarations, including comments. This creates a harsh authoring constraint: a developer cannot write a comment like "the old `/settings/github` route is now a redirect" without failing CI. The brief acknowledges this ("a new comment such as 'redirects /settings/integrations' must not be written outside the two redirect-only files"). This is intentional per the brief, but it is worth flagging that the constraint may frustrate future maintenance (e.g., a developer adding a migration note in a comment). The brief should consider whether the grep should exclude comments, or whether the prohibition should be enforced by a lint rule that only checks string literals in `Link`/`redirect` targets.

**[W-2]** The brief says "No API, database or OpenAPI schema change. Do not touch `crates/`, `migrations/` or `docs/openapi/`", but the Operating rules say "All `gh` calls pass `--repo Performant-Labs/gridops`; never touch upstream iamngoni/gridops." This is a workflow constraint, not a scope constraint, and it is listed under Operating rules, not Scope. A reviewer should confirm that the "never touch upstream" rule is not intended to be tested by an acceptance criterion, as it would be unverifiable from the code itself. The brief does not list this as an acceptance criterion, so it is advisory. This is fine, but the brief should consider whether the upstream rule belongs in the scope section (it is a hard limit) rather than only in Operating rules.
